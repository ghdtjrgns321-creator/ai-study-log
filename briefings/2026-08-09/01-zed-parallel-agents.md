# 오늘의 AI 개념: 제드 병렬 에이전트(Zed Parallel Agents)와 에이전트 클라이언트 프로토콜(ACP)

> 작성일: 2026-08-09 · 분류: agentic-coding

## 한 줄 정의

제드(Zed) 병렬 에이전트는 하나의 에디터 창 안에서 클로드 코드·코덱스·커서·앰프(Amp) 등 서로 다른 벤더의 코딩 에이전트를 동시에 여러 개 실행하고, 스레드 단위로 관리하는 기능이다.

## 쉬운 설명

지금까지 코딩 에이전트를 여러 개 동시에 돌리려면, 터미널 창을 여러 개 띄우거나 에디터 창 자체를 복제해야 했다. 클로드 코드 사용자가 병렬 작업을 하려면 깃 워크트리(Git Worktree)로 디렉터리를 나누고 터미널 세션을 각각 열어야 했던 것과 같은 방식이다.

제드는 이 문제를 에디터 안으로 끌어들였다. 스레드 사이드바라는 패널 하나에서 여러 에이전트 스레드를 나란히 띄워놓고, 각 스레드가 어떤 프로젝트·어떤 브랜치에서 작업 중인지 한눈에 보며 전환할 수 있다.

비유하자면 예전에는 직원마다 회의실을 따로 잡아 각자 다른 업체 컨설턴트를 불러 상담했다면, 이제는 사무실 한쪽에 상황판을 두고 여러 컨설턴트의 진행 상황을 동시에 지켜보며 필요할 때만 끼어드는 방식이 된 것이다.

기존 클로드 코드의 에이전트 팀즈(Agent Teams, 2026-07-15 소개)나 깃 워크트리 기반 병렬 실행(2026-07-31 소개)과 다른 점은, 제드는 하나의 벤더 안에 갇히지 않고 클로드·코덱스·커서 등 외부 에이전트를 그대로 가져와 에디터가 이들을 동시에 호스팅하는 "에이전트에 중립적인 에디터"를 지향한다는 것이다.

## 동작 원리

제드는 에이전트 클라이언트 프로토콜(Agent Client Protocol, ACP)이라는 개방형 인터페이스를 통해 외부 에이전트를 연결한다. 동작 순서는 다음과 같다.

1. 사용자가 에디터에서 프로젝트를 열고 스레드 사이드바에서 새 스레드를 만든다.
2. 스레드마다 사용할 에이전트(제드 자체 에이전트, 클로드, 코덱스, 커서, 오픈코드 등)를 선택한다.
3. 각 스레드는 독립된 컨텍스트 창과 대화 이력을 가지고 병렬로 실행되며, 완료되면 사이드바에 안 읽음 표시(파란 점)가 뜬다.
4. 격리가 필요한 작업은 스레드 생성 시 새 깃 워크트리를 자동으로 만들어, 원본 체크아웃을 건드리지 않고 별도 디렉터리에서 진행한다.
5. 작업이 끝나면 스레드를 보관(archive)할 수 있는데, 이때 커밋되지 않은 변경분은 깃 저장소 안에 임시 커밋 형태로 보관되고 빌드 산출물 같은 무시 대상 파일은 디스크에서 정리된다.

## 구체 예시·사례

공식 데모 영상에서는 실제로 하나의 프로젝트에서 세 개의 에이전트를 동시에 돌리는 과정을 보여준다. 먼저 제드 자체 에이전트에게 "리드미(README)를 근거로 이 프로젝트를 설명해달라"고 시키고, 이 작업이 끝나기 전에 같은 화면에서 클로드 에이전트에게 같은 질문을 다시 시키고, 이어서 커서 에이전트로 세 번째 스레드를 띄운다.

이후 별도 프로젝트(planets 디렉터리)에서는 새 깃 워크트리를 만들어 "extensions라는 개념을 plugins로 전부 바꿔달라"는 대규모 리네이밍 작업을 에이전트에게 맡기고, 작업이 진행되는 동안 다른 프로젝트로 전환해 별개의 작업을 계속한다. 완료 후에는 브랜치 diff로 변경 내역을 검토하고, 새 브랜치를 만들어 커밋·푸시까지 진행한다.

## 비슷한 것과 비교

| 구분 | 깃 워크트리 병렬 실행(CLI) | 클로드 코드 에이전트 팀즈 | 제드 병렬 에이전트 |
|---|---|---|---|
| 실행 단위 | 터미널 세션 + 디렉터리 분리 | 단일 벤더 내 서브에이전트 오케스트레이션 | 에디터 내 스레드 사이드바 |
| 에이전트 범위 | 클로드 코드 중심 | 클로드 코드 자체 서브에이전트 | 클로드·코덱스·커서·앰프 등 멀티벤더 |
| 격리 방식 | 사용자가 직접 워크트리 생성 | 세션 예산·권한으로 격리 | 스레드 생성 시 워크트리 자동 생성 |
| 시각화 | 없음(터미널 각각 확인) | CLI 로그 | GUI로 실시간 diff·상태 확인 |

선택 기준: 터미널 환경에서 스크립트 기반 자동화까지 원한다면 워크트리 CLI 방식이 유연하고, 여러 벤더의 에이전트 품질을 비교하며 GUI로 관리하고 싶다면 제드 쪽이 진입장벽이 낮다.

## 왜 지금 중요한가

제드는 2026년 4월 29일 5년간의 개발 끝에 1.0을 출시했고, 병렬 에이전트 기능은 그 직전인 4월 22일 별도로 공개됐다. 오픈소스로 제공되며 러스트(Rust) 기반 자체 GPU 렌더링 엔진(GPUI)을 사용해 외부 플랫폼에 의존하지 않는 성능을 강조한다.

ACP처럼 에디터와 에이전트 엔진을 분리하는 개방형 프로토콜이 자리 잡으면, 코딩 에이전트 시장이 특정 벤더에 종속된 폐쇄형 구조에서 벗어나 "엔진은 자유롭게 선택하고 인터페이스만 표준화"되는 방향으로 재편될 가능성이 있다는 점에서 에이전틱 코딩 툴링 전반에 영향을 줄 수 있는 움직임이다.

## 회계법인 AI 직무 연결 포인트

회계·감사 실무자가 직접 코드를 짤 일은 많지 않지만, 내부 감사팀이나 회계정보시스템(AIS) 부서가 데이터 검증 스크립트·RPA 자동화를 개발할 때는 이런 멀티 에이전트 병렬 개발 흐름을 참고할 수 있다. 예를 들어 표본추출 스크립트를 한 에이전트가 작성하는 동안 다른 에이전트에게 검증 테스트 코드를 병렬로 맡기는 식의 업무 분담이 가능해진다.

또한 여러 벤더의 에이전트를 같은 작업에 붙여 결과를 비교하는 구조는, 감사 업무에서 AI 산출물을 단일 도구에만 의존하지 않고 교차 검증하는 관행과 맞닿아 있다. 벤더 종속 없이 도구를 교체·비교할 수 있다는 점은 조달·거버넌스 관점에서도 참고할 만하다.

## 핵심 용어·논쟁

- **ACP(Agent Client Protocol)** — 에디터가 특정 에이전트 구현에 얽매이지 않고 여러 코딩 에이전트를 표준화된 방식으로 붙일 수 있게 하는 개방형 인터페이스.
- **스레드 사이드바(Threads Sidebar)** — 여러 에이전트 스레드를 프로젝트별로 그룹화해 보여주는 제드의 새 패널.
- **워크트리(Worktree)** — 하나의 깃 저장소에서 브랜치별로 독립된 작업 디렉터리를 만드는 기능으로, 병렬 작업 간 파일 충돌을 막는다.
- **스레드 보관(Archive Thread)** — 완료된 스레드의 미커밋 변경분을 깃 저장소에 임시 커밋으로 남기고 디스크상의 무시 대상 파일을 정리하는 기능.

진행 중인 쟁점은 "에디터가 에이전트를 호스팅하는 구조"와 "에이전트가 에디터 없이 터미널에서 자립적으로 동작하는 구조(클로드 코드류)" 중 어느 쪽이 실무 표준이 될지다. 전자는 시각적 관리와 멀티벤더 비교에 유리하지만, 후자는 서버·CI 환경에서 헤드리스로 돌리기 쉬워 자동화 파이프라인에 더 적합하다는 반론이 있다.

가장 좋은 자료 두 개는 제드 공식 블로그의 병렬 에이전트 공지문과 1.0 출시문이며, 여기에 실제 시연 영상을 더해 요약했다.

### Introducing Parallel Agents in Zed — 영어, 공식 블로그, 중급
스레드 사이드바의 구조와 사용법, 외부 에이전트 가져오기, 워크트리 자동 생성, 스레드 보관 시 디스크 정리 방식을 설명한다. 기본 레이아웃이 바뀌어 프로젝트·깃 패널이 오른쪽으로, 스레드 사이드바와 에이전트 패널이 왼쪽으로 재배치됐다는 실무 팁도 담겨 있다.

### Zed is 1.0 — 영어, 공식 블로그, 중급

## 자가 점검 질문

1. ACP가 해결하려는 문제는 무엇이며, 기존 클로드 코드의 서브에이전트 구조와 어떤 지점에서 다른가.
2. 감사팀이 데이터 검증 스크립트를 여러 에이전트로 병렬 개발한다면, 어떤 부분을 교차 검증 대상으로 삼아야 하는가.
3. 에이전트를 에디터가 호스팅하는 구조는 CI·서버 환경의 헤드리스 자동화에 어떤 한계를 가질 수 있는가.
