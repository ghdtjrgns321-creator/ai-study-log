개인 개발자 채널 "bri"가 올린 19분 56초짜리 실전 튜토리얼이다. Claude Code(또는 Codex)로 여러 작업을 동시에 진행할 때 왜 단순히 터미널을 두 개 여는 방식이 실패하는지 짚고, git worktree로 이를 해결하는 전체 과정을 실제 화면 녹화로 보여준다.

## 다루는 내용 순서

1. **문제 제기 — 왜 터미널 두 개로는 안 되는가**
   백로그에는 서로 의존하지 않는 작업이 여러 개 있어 하나가 끝나야 다음을 시작할 필요가 없는 경우가 많다. 하지만 터미널 두 개에서 Claude Code를 각각 실행하면 두 에이전트가 같은 작업 디렉터리의 같은 파일을 동시에 읽고 쓰게 되어, 한쪽이 수정하는 동안 다른 쪽이 그 이유를 모른 채 절반만 수정된 파일을 읽어버리고 결국 코드가 깨진다.

2. **git worktree의 원리 — object store와 working tree의 분리**
   git 저장소는 커밋·히스토리·브랜치를 담는 "object store"와, 실제로 디스크에 보이는 파일들인 "working tree" 두 가지로 구성된다. 평소에는 이 둘이 1:1로 묶여 있어 브랜치를 바꾸면 파일도 그 브랜치에 맞게 바뀌고, 한 컴퓨터의 한 디렉터리는 한 번에 하나의 브랜치만 표시할 수 있다. git worktree는 이 결합을 풀어, object store(히스토리)는 하나만 유지한 채 working tree(파일)는 여러 개를 동시에 둘 수 있게 한다. 각 working tree는 서로 다른 브랜치를 체크아웃한, 컴퓨터 상의 완전히 별도인 디렉터리다. 영상은 이를 "메인 저장소는 원본(source of truth), worktree는 그 원본의 위성(satellite)"이라는 비유로 설명한다 — 같은 히스토리와 리모트를 공유하지만 디스크상의 파일은 공유하지 않는다.

3. **worktree 목록 확인 — `git worktree list`**
   활성 git 저장소 디렉터리에서 `git worktree list`를 입력하면 현재 연결된 모든 worktree와 그 디렉터리 경로, 체크아웃된 브랜치가 나열된다. 처음 시작하는 사람은 `main` 하나만 보인다.

4. **첫 worktree 생성 — `git worktree add`**
   저장소 디렉터리에서 한 단계 위로 이동한 뒤, `git worktree add ../프로젝트명-기능명 -b 새브랜치명 origin/staging`(또는 `origin/main`) 형식으로 새 worktree를 만든다. 실행하면 새 브랜치가 생성되고 지정한 베이스 브랜치의 최신 커밋을 가리키는 head가 설정된다. `git branch`를 입력하면 새로 열린 worktree에 연결된 브랜치가 색상(teal)으로 구분되어 표시된다.

5. **디렉터리·브랜치 네이밍 규칙**
   영상 제작자는 모든 worktree 디렉터리 이름 앞에 프로젝트 이름을 붙여(`ls` 했을 때 한곳에 모여 보이도록) 관리하고, 각 worktree 이름은 그 worktree에서 구현할 기능명과 일치시킨다. 이렇게 하면 여러 터미널을 동시에 열어놓아도 어디서 무슨 작업을 하는지 혼동하지 않고, 실수로 다른 브랜치의 작업 범위와 겹치는 것도 방지할 수 있다.

6. **실전 예시 — 두 worktree를 동시에 운용**
   실제로 "dashboard creation"(백엔드, DeFi Llama 연동 추가)과 "HubSpot access"(프론트엔드, UI에 전체선택/해제 체크박스 추가) 두 개의 worktree를 화면 분할로 동시에 보여준다. 각 worktree 디렉터리로 이동해 Codex(Claude Code와 동일하게 동작한다고 설명)를 열고 서로 다른 작업 지시를 내린다. 한쪽 세션이 실수로 별도 브랜치로 전환하려 하자, 제작자는 "아니오, 같은 브랜치에 있고 싶다"고 답하며 에이전트의 제안을 항상 확인하고 필요하면 거부해야 한다는 점을 강조한다.

7. **결과 확인과 병합**
   두 세션이 끝난 뒤 각 디렉터리에서 `git status`를 확인하면, 한쪽은 PHP 등 백엔드 파일만, 다른 한쪽은 HTML/CSS 등 프론트엔드 파일만 변경된 것을 볼 수 있어 서로 영향을 주지 않았음이 확인된다. 이후 각 브랜치를 커밋하고 GitHub에서 staging 브랜치로 PR을 만들어 병합한다. 다만 여러 에이전트가 같은 파일을 건드리는 경우 병합 충돌(merge conflict)이 발생할 수 있다는 점은 유의사항으로 짚는다.

8. **고급 패턴 1 — 프로젝트 컨텍스트 MD 파일**
   Claude는 루트에 `CLAUDE.md`, Codex는 `AGENTS.md` 파일로 프로젝트 전체에 적용되는 지침을 정의한다. 이 파일이 있으면 새로 만드는 모든 worktree에 별도 설정 없이 자동으로 프로젝트 컨텍스트가 적용된다. 여기에 더해 worktree 루트에 그 worktree 전용의 추가 MD 파일을 두면, 해당 기능에 국한된 범위 지정 컨텍스트(scoped context)를 줄 수 있다.

9. **고급 패턴 2 — 에이전트 대 에이전트 비교(가장 강조하는 패턴)**
   제작자가 "가장 유용하다"고 꼽는 패턴은 단순 병렬 작업이 아니라 "비교"다. 완전히 동일한 작업을 두 개의 별도 worktree에서 서로 다른 에이전트(또는 같은 에이전트의 두 번의 시도)에게 맡긴 뒤, 두 결과물을 비교해 더 나은 쪽을 채택하고 나머지는 버린다. 특히 여러 타당한 접근법이 있는 아키텍처 결정에서 유용하며, 두 접근을 모두 구현해보는 데 드는 비용이 "시간이 두 배"가 아니라 "같은 시간에 기회비용만 절반"이 되는 효과를 낸다고 설명한다.

10. **고급 패턴 3 — tmux와 결합**
    여러 에이전트를 정기적으로 운용한다면 tmux를 함께 배우는 것이 좋다고 권한다. `brew install tmux`로 설치한 뒤, `tmux new-session -s 세션이름 -c 디렉터리경로` 형식으로 각 worktree마다 이름이 붙은 세션을 만들면, 터미널을 닫아도 에이전트 세션이 유지되고 `tmux ls`로 모든 활성 세션과 연결 상태(attached/detached)를 한눈에 확인할 수 있다.

11. **worktree를 언제 쓰고 언제 쓰지 않는가 — 마무리 정리**
    - 쓸 때: 오늘 처리할 작업이 두 개 이상이고 서로 같은 파일을 공유하지 않을 때. 또는 하나의 접근법을 바로 확정하기보다 위험도가 높아 두 가지 접근을 모두 보고 싶을 때.
    - 안 쓸 때: 작업 하나가 코드베이스 전체에 걸쳐 있을 때, 또는 작업 성격이 탐색적이라 에이전트가 코드베이스 전체를 자유롭게 돌아다녀야 할 때는 단일 세션을 유지하는 편이 낫다.
