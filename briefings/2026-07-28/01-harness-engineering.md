# 오늘의 AI 개념: 하네스 엔지니어링(Harness Engineering)

> 작성일: 2026-07-28 · 분류: agentic-coding

## 한 줄 정의

하네스 엔지니어링은 AI 코딩 에이전트가 실수 없이 원하는 결과를 내도록, 모델을 둘러싼 맥락·도구·검증 절차 전체를 설계하는 작업이다.

## 쉬운 설명

이 개념은 "Agent = Model + Harness"라는 공식으로 요약된다. 하네스란 에이전트를 구성하는 요소 중 모델 자체를 뺀 나머지 전부, 즉 컨텍스트·도구·실행 루프·검증 절차·사람의 개입 지점을 가리킨다.

비유하자면 하네스는 원래 마부가 말에게 씌우는 고삐·안장·굴레를 뜻하는 말이었다. 고삐가 방향을 지시하듯 프롬프트와 시스템 컨텍스트가 에이전트의 작업 방향을 정하고, 도구 지급이 실행 능력을 부여하며, 가드레일(제약 규칙)이 굴레처럼 행동 범위를 제한한다.

같은 모델(예: 같은 요금제의 Opus)을 써도 어떤 팀은 결과물이 MVP 수준에 머물고 어떤 팀은 배포 가능한 서비스까지 만들어내는 차이가 여기서 갈린다. 모델은 동일하게 제공되지만, 모델을 돌리는 환경 설계 수준이 다르기 때문이다.

기존의 프롬프트 엔지니어링·컨텍스트 엔지니어링과는 포함 관계에 있다. 컨텍스트 엔지니어링은 하네스가 에이전트에게 가이드와 센서를 제공하는 하나의 수단일 뿐이고, 하네스 엔지니어링은 그 위에 실행 루프 설계, 자동 검증, 사람의 역할 배치까지 포괄하는 상위 개념이다.

## 동작 원리

1. 사람이 최종 목표와 중간 검증 기준을 함께 준다.
2. 에이전트가 그 기준을 만족시키기 위해 코드베이스를 탐색·수정·생성한다.
3. 정해진 검증(테스트, 린트 등)을 통과하는지 자동으로 확인하고, 실패하면 다시 탐색·수정을 반복한다.
4. 스스로 목표를 달성하기 어렵다고 판단되면 사람에게 에스컬레이션한다.

잘 만든 하네스는 다음 세 축으로 점검한다.

- **컨텍스트**: 컨텍스트 윈도우는 한정된 예산이므로, 작업 목표·제약 조건·코딩 컨벤션처럼 처음부터 반드시 필요한 정보와, 상세 코드나 로그처럼 필요할 때만 도구로 불러올 정보를 구분해서 설계한다. 저장소 최상위의 안내 문서(예: AGENTS.md)는 상세 내용을 다 담기보다 "어디에 무엇이 있는지"를 알려주는 목차 역할만 하도록 가볍게 유지한다.
- **도구**: 기본 제공 도구보다 성능이 검증된 도구를 골라 쥐여주고, 도구가 낸 에러 메시지는 반드시 모델에 전달한다. 승인 기반 루프로 에이전트의 행동 범위를 통제하되, 반복된 승인 요청에 사람이 지쳐 검토 없이 클릭하게 되는 "승인 피로"를 별도로 경계해야 한다.
- **평가(Evaluation)**: 결과물과 그 결과물이 나온 과정을 함께 측정한다. 같은 세션·같은 모델이 자신의 결과를 스스로 채점하면 관대해지는 "자기평가 편향"이 있으므로, 채점은 다른 모델이나 별도 세션에서 교차 검증하는 방식을 권장한다.

## 구체 예시·사례

Anthropic이 자사 블로그에서 공개한 실험이 하네스의 효과를 잘 보여준다. 아무런 하네스 없이 명령만 내렸을 때는 약 9달러의 비용으로 20분 만에 작업이 끝났지만, 실행되지 않는 결과물이 나왔다.

반면 컨텍스트·도구·평가 루프를 갖추고 멀티에이전트로 구성한 하네스를 사용했을 때는 총 200달러의 비용으로 6시간에 걸쳐 16개 기능을 구현했고, 여러 스프린트를 정상적으로 거쳐 실제로 실행되는 게임을 완성했다. 이 블로그 글의 표현을 빌리면 "우리는 에이전트를 평가할 때 하네스와 모델의 결합을 함께 평가한다."

동일한 원칙이 실무에서는 Claude Code와 Codex를 역할 분담시키는 방식으로도 나타난다. 예컨대 계획 수립과 1차 검증은 계획·검증 능력이 강한 모델에 맡기고, 1차 코드 작성은 코딩에 강한 모델에 맡긴 뒤, 서로 다른 모델이 서로의 결과물을 교차 검증하게 해 자기평가 편향을 구조적으로 차단하는 식이다.

## 비슷한 것과 비교

| 구분 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 | 하네스 엔지니어링 |
|---|---|---|---|
| 다루는 범위 | 한 번의 지시문 문구 | 컨텍스트 윈도우에 무엇을 채울지 | 컨텍스트+도구+실행 루프+검증+사람 역할 전체 |
| 개선 대상 | 단발성 응답 품질 | 모델이 참조하는 정보의 질과 양 | 반복 작업에서 신뢰할 수 있는 산출물이 나오는 시스템 |
| 실패 대응 | 프롬프트를 다시 씀 | 넣을 정보를 다시 선별함 | 자동 검증·재시도·에스컬레이션 루프가 대응 |
| 사람의 위치 | 매번 결과를 보고 다시 지시 | 필요한 문서를 미리 정리 | 팀장처럼 에이전트를 관리하는 역할로 이동 |

선택 기준은 "한 번 잘 되는 답"이 목표면 프롬프트·컨텍스트 엔지니어링으로 충분하지만, 여러 번 반복해도 신뢰할 수 있는 결과가 필요하면 하네스 엔지니어링까지 설계해야 한다는 것이다.

## 왜 지금 중요한가

OpenAI는 공식 블로그 "Harness engineering: leveraging Codex in an agent-first world"에서 이 개념을 공식화했다. 짧은 메모 형태의 초판은 2026년 2월 17일에, 전체 아티클은 2026년 4월 2일에 공개됐다. 같은 시기 소프트웨어 엔지니어링 전문지 Martin Fowler의 사이트에도 "Harness engineering for coding agent users"라는 심화 아티클이 실려 업계 논의가 확산됐다.

업계 동향도 이를 뒷받침한다. 2026년 7월 기준 여러 AI 코딩팀은 특정 벤더에 종속되지 않기 위해 Claude Code·Codex·OpenCode·Aider 등 여러 하네스에 공통으로 적용할 수 있는 표준 프롬프트·정책·평가·텔레메트리 체계를 구축하는 "하네스 우선" 접근을 취하고 있다는 분석이 나온다.

- [Harness engineering: leveraging Codex in an agent-first world (OpenAI)](https://openai.com/index/harness-engineering/)
- [Harness engineering for coding agent users (Martin Fowler)](https://martinfowler.com/articles/harness-engineering.html)

## 회계법인 AI 직무 연결 포인트

감사 업무에 에이전트를 투입할 때 "프롬프트만 잘 쓰면 된다"는 접근은 위험하다. 계정 대사나 이상거래 탐지처럼 반복되는 업무일수록, 무엇을 검증 기준으로 삼을지(테스트 통과가 아니라 회계기준 부합 여부)와 누가 언제 무엇을 승인했는지를 자동으로 남기는 하네스 설계가 감사 품질을 좌우한다.

승인 기반 루프 설계는 내부통제 문서화 요구와 직접 연결된다. 에이전트가 특정 폴더나 데이터에 접근하지 못하도록 하는 가드레일, 그리고 그 승인·거부 이력을 남기는 절차는 그대로 통제 활동(control activity)의 증적으로 쓰일 수 있다.

자기평가 편향을 막기 위한 교차 검증 원칙은 감사인의 이중 검토(review) 관행과 본질적으로 같은 발상이다. AI가 만든 초안을 같은 AI가 스스로 승인하게 하면 안 된다는 원칙은, 담당자와 검토자를 분리하는 감사 절차의 기본 원리와 그대로 겹친다.

## 핵심 용어·논쟁

- 하네스(Harness) — 에이전트를 구성하는 요소 중 모델을 제외한 컨텍스트·도구·루프·사람의 역할 전체.
- 컨텍스트 엔지니어링(Context Engineering) — 한정된 컨텍스트 윈도우에 무엇을 넣을지 설계하는, 하네스를 구성하는 하위 기술.
- 평가 주도 개선(Evaluation-Driven Improvement) — 결과물과 그 산출 과정을 함께 측정해 반복 개선하는 원칙.
- 자기평가 편향(Self-grading bias) — 같은 모델·세션이 자신의 결과를 채점할 때 생기는 낙관적 편향.
- 승인 피로(Approval fatigue) — 반복된 승인 요청에 지쳐 검토 없이 승인 버튼을 누르게 되는 위험.

가장 뜨거운 쟁점은 하네스가 정교해질수록 "개발자"라는 직함의 의미가 코드 작성자에서 에이전트 환경 설계자로 옮겨간다는 전망이다. 이는 아직 업계 합의가 아니라 실무자 개인의 관측에 가까우며, 그 속도가 예상보다 빠를지 느릴지에 대한 의견은 갈린다.

## 자료 깊이 읽기

### Harness engineering: leveraging Codex in an agent-first world — 영어, 공식 블로그, 중급

OpenAI가 하네스라는 용어를 "Agent = Model + Harness"로 정식화한 글이다. 하네스를 사전 예방형 제어(가이드)와 사후 교정형 제어(센서)로 나누고, 각각을 결정적(테스트·린터 등 계산형)과 의미론적(AI 코드 리뷰 등 추론형)으로 다시 구분한다. 유지보수성·아키텍처 적합성·동작이라는 세 가지 통제 범주를 제시하며, 엔지니어의 역할이 코드 로직 작성에서 환경·의도·피드백 루프를 설계하는 쪽으로 이동한다고 주장한다.

### Harness engineering for coding agent users — 영어, 아티클, 중급

Martin Fowler 사이트에 실린 심화 글로, 하네스를 가이드(guide)와 센서(sensor)로 나누는 프레임을 제시한다. 컨텍스트 엔지니어링이 하네스 구현의 수단이라는 관계를 명확히 하고, 초판 메모(2026-02-17)에서 전체 아티클(2026-04-02)로 발전한 논의 과정을 통해 개념이 다듬어진 배경을 확인할 수 있다.

## 자가 점검 질문

1. 하네스 엔지니어링이 프롬프트 엔지니어링·컨텍스트 엔지니어링과 어떻게 다르며, 왜 상위 개념으로 볼 수 있는가.
2. 감사 업무 자동화 파이프라인을 설계한다면, 검증 기준과 승인 이력을 어떤 방식으로 하네스에 내장시킬 것인가.
3. 자기평가 편향을 막기 위한 교차 검증 구조를 실제 팀에 도입할 때 예상되는 비용·시간상의 트레이드오프는 무엇인가.
