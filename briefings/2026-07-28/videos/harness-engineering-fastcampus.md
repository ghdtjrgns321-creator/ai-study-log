## 도입 — 왜 같은 모델로도 결과물 격차가 나는가

발표자는 같은 AI 도구(같은 요금제, 같은 모델)를 써도 어떤 팀·개인은 바이브 코딩 수준의 MVP에서 멈추고, 어떤 팀·개인은 배포 가능한 운영 서비스까지 만들어낸다는 문제의식에서 출발한다. 모델은 동일하게 제공되므로, 차이는 모델을 돌리는 "환경"에 있다는 것이 핵심 전제다.

영상은 다섯 가지 순서로 진행된다: (1) 하네스 엔지니어링의 정의, (2) 성능 격차를 만드는 세 가지 축, (3) Claude Code와 Codex의 차이와 사용처, (4) 이 둘을 조합한 실전 개발 패턴, (5) 그럼에도 사람이 필요한 이유.

## 1. 하네스 엔지니어링의 정의

하네스는 모델을 둘러싼 모든 것이라고 정의한다. 원래 에이전트를 구성하는 요소로 "툴(tool)"이라는 개념이 있었는데, 그 범주를 확장한 것이 하네스다. 구성 요소는 컨텍스트, 기존에 쓰던 도구(MCP·스킬 등), 실행 루프, 그 루프 안에서 작업 완료 여부를 검증하는 절차, 그리고 사람까지 포함한다. 사람 역시 하네스의 한 부분으로, 어떤 역할을 맡을지, 검증 프로세스를 어떻게 구성할지, 도구는 무엇을 지급할지, 시스템 프롬프트는 어떻게 줄지를 모두 설계 대상으로 본다.

OpenAI 하네스 엔지니어링 블로그의 표현을 인용해, 엔지니어의 주요 업무가 "코드 로직을 작성하는 것"에서 "환경·의도·피드백을 루프 형태로 설계하는 설계자 역할"로 넘어갔다고 강조한다.

하네스라는 단어의 어원도 짚는다. 전통적으로 하네스는 마부가 말에게 씌우는 장비(고삐, 안장, 굴레)를 뜻했다. 고삐는 방향 지시, 안장은 사람이 탑승하는 위치, 굴레는 통제 범위를 정하는 역할을 했는데, 이를 AI 에이전트에 적용하면 프롬프트·시스템 컨텍스트가 방향 지시(고삐), 도구 지급이 실행 능력 부여, 제약·가드레일이 통제 범위(굴레)에 대응한다고 설명한다.

기존 IDE(커서 등)의 채팅 기반 작업 방식과 대비도 제시한다. 기존에는 사람이 요청 → 모델 결과 확인 → 문제 발견 시 사람이 직접 드래그·링크로 다시 설명 → 반복, 이라는 과정을 거쳐야 했고 자동으로 문제를 찾는 개념이 없어 사람이 쉽게 지쳤다. 하네스는 이 과정을 자동화한다: 목표와 중간 검증 기준을 주면, 에이전트가 코드베이스를 탐색·수정·생성하고, 검증 기준으로 계속 재시도하다가, 스스로 목표 달성이 어렵다고 판단하면 그때 사람에게 요청한다. 발표자는 이를 팀장에게 중간보고하고 방향 지시를 받은 뒤 최종 결과물을 들고 가는 과정에 비유하며, 사람의 역할이 "실무자"에서 "에이전트를 관리하는 팀장"으로 바뀐다고 표현한다.

## 2. 성능 격차를 만드는 세 가지 축

### 축 1 — 컨텍스트

컨텍스트는 무조건 많이 넣는다고 좋은 것이 아니라 한정된 예산이라는 전제에서 출발한다. 모델의 컨텍스트 윈도우가 아무리 커져도(옵서스가 1백만 토큰, GPT도 최소 272K~1백만 토큰까지 확장) 체감상 300K를 넘어가면 결과물의 질이 떨어진다고 언급한다. 이는 트랜스포머 구조가 오토리그레시브(자기회귀)하게 동작해 문장이 길어질수록 연산량이 늘고, 연산량이 늘수록 오류 확률이 높아지는 구조적 특성 때문이라고 설명한다. 그래서 Codex·Claude Code 같은 도구는 컨텍스트가 약 95% 차면 자동으로 압축하는데, Claude는 이 자동 압축을 끌 수 있지만 Codex는 끌 수 없다는 차이도 짚는다.

컨텍스트를 두 종류로 나눈다.
- **처음부터 바로 주입해야 하는 컨텍스트**: 작업 목표, 제약 사항(constraint), 전체 코딩 컨벤션, 최근 아키텍처 변경 내역, 절대 하면 안 되는 행동이나 접근 금지 폴더 같은 위험 규칙.
- **필요할 때만 도구로 가져오는 컨텍스트**: 상세 코드 내용, 대용량 로그, 공식 문서·API 레퍼런스, 테스트 실행 결과나 에러 트레이스. 특히 테스트 실행 결과는 "성공/실패"만 반복 출력되며 컨텍스트를 불필요하게 많이 차지하므로, 필요하지 않으면 가져오지 않는 편이 낫다고 강조한다.

발표자가 실제로 쓰는 문서 구조도 공유한다. 레포지토리 최상위에 "에이전트.md"(Claude Code의 CLAUDE.md에 해당) 문서를 두되, 이 문서에는 상세 내용을 담지 않고 책의 목차처럼 "어디에 어떤 문서가 있는지"만 가볍게 담는다. 세부 내용은 하위 문서(아키텍처 문서, 프로덕트 스펙, 레�런스 문서, 실행 계획 문서, 품질 스코어 문서, 보안 규칙 문서)에 나눠 담고, 필요할 때만 펼쳐 읽게 한다. 특히 "실행 계획(execute plan)" 문서를 반드시 남겨야 한다고 강조하는데, 결과물(코드)은 깃허브 커밋으로 남지만 계획은 대화 세션에만 남고 저장되지 않기 때문에, 나중에 계획 자체가 잘못됐는지 판단이 잘못됐는지 회고하려면 계획을 강제로 파일로 저장해야 한다는 것이다.

### 축 2 — 도구와 환경 설계

환경(environment) 설계를 간과하는 경우가 많다고 지적한다. 예컨대 승인 없이 모든 작업을 자동 실행하는 "바이패스 모드"를 처음부터 알려주지 않고, 최소 일주일 정도는 승인 기반 루프로 작업이 이뤄진다는 것을 사용자가 체감하게 한 뒤에야 알려준다고 소개한다.

도구 설정에서는 기본 제공 도구보다 성능이 검증된 도구를 선택해서 쓴다. 예를 들어 Claude Code의 기본 웹서치 도구 대신 성능이 더 좋다고 판단한 별도 검색 도구(Tavily, Exa Search 등)를 문서로 강제 지정해 도구 간 중복을 최소화한다. 도구가 낸 에러 메시지는 반드시 모델에 전달되도록 해서, 예를 들어 API 호출 한도를 다 썼는데 계속 호출을 시도하는 상황을 모델이 인지하게 한다.

승인 기반 루프와 관련해 위험 사례를 소개한다. Anthropic의 글을 인용하며, 승인 기반 루프에서 열 번째 승인부터는 사람이 더 이상 검토하지 않고 그냥 클릭만 하게 된다는 내용을 언급하고, 실제로 이로 인해 Claude Code의 전체 소스 코드가 NPM 저장소에 유출되는 사고가 발생했다고 전한다(영상 시점 기준 약 3일 전 사건으로 언급). 이 사고를 계기로 업계에서 "잘 만들어진 하네스는 어떤 모습인가"를 다시 살펴보게 됐다고 설명한다. 아울러 에이전트가 임의로 셸 명령을 만들어 실행하는 것의 위험성, 샌드박스에서 코드를 실행하고 결과가 안전하다고 판단될 때만 실제 파일로 반영하는 방식, MCP 도구 오염 공격이 지속적으로 발생하고 있다는 점도 짚는다.

### 축 3 — 평가(Evaluation) 주도 개선

"느낌"으로 코드베이스를 개선해서는 안 되고, 결과물과 그 결과물이 나오는 과정 전체의 품질을 측정해야 한다고 강조한다. 평가 절차는 어떤 작업을 어떻게 평가할지 정의 → 여러 번 실행 → 채점 → 전체 실행 과정 기록 → 최종 결론 도출의 흐름을 따른다.

가장 크게 경계해야 할 함정으로 "자기평가 편향"을 꼽는다. 같은 세션에서 방금 코드를 작성한 모델에게 그 결과를 스스로 평가하게 하면, 편향이 발생해 실제로는 미흡한 작업에도 "완료했습니다"라고 자신 있게 답한다는 것이다. 그래서 발표자가 생각하는 권장 아키텍처는: 사용자가 스펙(요구사항)만 가볍게 입력 → 코드로 정의된 하네스 컨트롤(루프·라우팅·정책) → 도구 실행 → 결과 검증(테스트·린팅) → 전 과정 모니터링, 의 흐름이다.

## 3. Claude Code와 Codex 비교

발표자의 체감 평가는 다음과 같다.

| 구분 | Claude Code | Codex |
|---|---|---|
| 강점 | 코드 작성(페어 프로그래머형) | 계획 수립, 컨텍스트 탐색, 검증·오케스트레이션 |
| 특징 | 티켓(구체 지시)이 없으면 스스로 작업을 잘 시작하지 않음 | GPT 5.4 버전 이후 계획·검증 능력이 강해짐 |

실전에서는 계획은 함께 짜되, 1차 코드 작성은 Claude Code가 맡고, 1차 검증과 수정은 Codex가, 2차 검증은 다시 Claude Code가, 최종 검증은 Codex가 맡는 교차 방식을 쓴다고 소개한다. 원칙은 "같은 모델이 만든 것을 같은 모델이 검증하지 않는다"이며, 이는 자기평가 편향을 구조적으로 막기 위함이다. Gemini는 코드 작성 능력이 아쉬워 잘 쓰지 않는다고 언급한다.

OpenAI가 최근 Codex를 Claude Code에서 플러그인 형태로 직접 호출할 수 있게 지원하기 시작해, 기존에 MCP로 직접 연동하던 방식을 대체했다고 언급한다.

## 4. 실전 개발 패턴 — 사람이 개입하는 지점

탐색 단계에서는 Claude Code와 Codex를 동등하게 쓰지만, 코드 구현은 Claude Code를 우선한다. 계획(스펙 기반 개발, SDD)을 다듬는 단계에서는 계획이 모호할 경우 반드시 사람에게 되물어보도록 요청해, 모델이 일반적인 방향으로 임의로 구현하지 않고 발표자의 의도가 반영되도록 유도한다.

팀 단위 작업에서는 하네스에 쌓인 지식을 개인에게만 두지 않고 공유 가능한 아티팩트로 만든다. 팀 전체가 지켜야 할 규칙은 별도 저장소로 관리해 Git 서브모듈로 연결하고, 새 프로젝트가 만들어지면 항상 이 기준 문서가 자동 주입되게 한다. 유용한 작업 패턴이 발견되면 "스킬"로 만들어 팀 공유 저장소에 올려 팀원들이 재사용하거나 피드백을 남기게 한다. 린트·테스트 실행 같은 "진짜로 반드시 지켜야 하는 규칙"은 문서로만 남기지 않고 훅(hook)을 통해 세션 시작 시 강제로 실행되게 한다.

이슈 제기부터 PR 머지까지 사람·Claude Code·Codex가 번갈아 개입하는 파이프라인을 구성한다: 문제 제기(사람) → 병렬 실행(에이전트) → 검증(주로 Codex) → 평가(evaluation) 반복 → 리뷰·머지(사람 포함). 서로 다른 관점(사람, Claude, Codex)이 섞여 최종적으로 사람이 결정한다.

Anthropic이 자사 하네스 구성 효과를 정리한 최근 글(영상 기준 약 1주일 전 게시)도 소개한다. 하네스 없이 명령만 내렸을 때는 9달러, 20분 소요, 전혀 실행되지 않는 결과물이 나왔다. 반면 멀티에이전트로 잘 구성한 하네스를 썼을 때는 총 200달러, 6시간 소요, 16개 기능 구현, 여러 스프린트를 정상적으로 거쳐 실제로 플레이 가능한 게임이 완성됐다. 이 글에서 발표자가 인상 깊게 본 문구로 "우리는 에이전트를 평가할 때 하네스와 모델의 결합을 함께 평가한다"를 꼽는다.

## 5. 그럼에도 사람이 필요한 이유

마지막으로 측정(measurement)의 중요성을 강조한다. 어떤 도구를 쓰든 대화 세션이 어디서 얼마나 잘못됐는지 추적하지 않으면 평가할 수 없고, 평가할 수 없으면 개선도 불가능하다는 것이다. 발표자는 LLMOps 플랫폼(랭퓨즈)을 통해 팀 내 모든 Claude Code·Codex 사용 기록을 모으고, 주기적으로 세션 전체를 평가해 프롬프트나 스킬 개선점을 팀원과 논의한다고 소개한다.

발표자는 "2년 후"라는 표현으로 자신의 예측이 더 빨리 현실화할 수도 있다고 전망하며, 개발자라는 직함이 더 이상 코드를 작성하는 사람이 아니라 에이전트를 얼마나 잘 다루는가, 즉 에이전트가 일할 환경을 얼마나 탄탄하게 설계·유지하는가로 재정의될 것이라는 전망으로 마무리한다. 반복 업무를 가벼운 문서로 정리하는 것부터 시작해 자신만의 하네스를 만들어볼 것을 권한다.

## 확인 필요 표시

- "Claude Code 소스 코드 NPM 유출 사고"와 "Anthropic 하네스 효과 블로그"의 정확한 게시일·수치는 영상 내 구어체 언급을 그대로 옮긴 것으로, 원문 블로그를 통한 재확인이 필요하다.
- Gemini 관련 평가는 발표자 개인 경험에 근거한 주관적 의견이다.
