# 오늘의 AI 개념: AWS Kiro의 스펙 기반 개발(Spec-Driven Development)

> 작성일: 2026-07-30 · 분류: agentic-coding

## 한 줄 정의

AI에게 곧바로 코드를 작성시키는 대신, 무엇을 만들지에 대한 문서부터 먼저 작성하게 해서 나중에 딴 길로 새지 않게 만드는 개발 방식이다.

## 쉬운 설명

AWS Kiro는 2025년 하반기 프리뷰로 등장해 스펙 기반 개발(Spec-Driven Development)을 중심에 둔 AI 코딩 도구로 자리잡았다. 이 도구는 기능 하나를 만들 때마다 코드보다 먼저 requirements.md(요구사항), design.md(설계), tasks.md(구현 작업 목록) 세 문서를 순서대로 작성하게 한다. 요구사항 문서는 EARS(Easy Approach to Requirements Syntax, 쉬운 요구사항 작성법) 표기법이라는 정해진 문장 틀을 써서 사용자 스토리와 수락 기준을 적는다.

이는 사람이 먼저 "무엇을, 왜" 만들지 합의한 뒤에야 AI가 "어떻게" 만들지로 넘어가게 강제하는 구조다. 프롬프트만 던지고 결과를 봐가며 즉흥적으로 고치는 방식(흔히 "바이브 코딩"이라 불린다)은 초기 속도는 빠르지만, 프로젝트가 커질수록 AI가 만든 코드가 원래 의도에서 조금씩 벗어나는 문제(프로덕션 드리프트)가 쌓인다. Kiro는 이 문제를 코드 작성 전 단계에서 막으려는 접근이다.

비슷한 것과 비교하면 차이가 분명해진다. 일반 AI 코딩 어시스턴트(Amazon Q Developer의 기존 방식 포함)는 "채팅으로 묻고 제안받는" 형태였고, 결과물의 일관성은 전적으로 사람의 검토에 의존했다. Kiro는 요구사항·설계 문서 자체가 프로젝트에 남는 산출물이 되어, AI가 나중에 코드를 고칠 때도 그 문서를 근거로 삼는다.

AWS는 2026년 5월, 기존 Amazon Q Developer의 지원을 순차 종료하며 고객들을 Kiro로 유도하는 조치를 공식화했다. 신규 가입은 2026년 5월 15일부터 막혔고, 5월 29일부터는 Q Developer Pro에서 최신 모델(Opus 4.6)을 뺐으며, IDE 플러그인과 유료 구독 자체는 2027년 4월 30일에 완전히 종료된다.

## 동작 원리

Kiro의 스펙(Specs) 기능은 기능 하나를 만들 때마다 다음 순서로 문서를 쌓는다.

```
① requirements.md 작성 — EARS 표기법으로 사용자 스토리·수락 기준을 정의
② design.md 작성     — 기술 아키텍처와 구현 접근 방식을 문서화
③ tasks.md 작성      — 추적 가능한 개별 구현 단계로 쪼갬
④ 코드 구현          — 위 문서를 근거로 AI가 실제 코드를 작성
```

이 네 단계는 프로젝트 저장소의 `.kiro/steering/` 경로에 자동 저장되며, 개발자가 언제든 열어 수정할 수 있다. 여기에 더해 프로젝트 전체의 일관성을 유지하는 steering docs(product.md·structure.md·tech.md)가 배경 문서로 함께 관리되고, 반복 작업을 자동화하는 Agent Hooks와 외부 API·서비스를 연결하는 MCP(Model Context Protocol, 모델 컨텍스트 프로토콜) 통합 기능이 추가로 제공된다.

## 구체 예시·사례

AWS 공식 산업 블로그가 소개한 생명과학 기업 사례가 대표적이다. 이 기업은 신약 후보 탐색에 쓰이는 에이전트를 3주 만에 연구·개발(R&D) 단계에서 상용 운영 단계까지 끌어올렸다고 소개된다. 과정은 먼저 요구사항 문서로 "어떤 데이터를 근거로 후보 물질을 걸러낼 것인가"를 확정하고, 설계 문서로 파이프라인 구조를 정한 뒤, tasks.md로 쪼갠 단위 작업을 Kiro가 순서대로 구현하는 흐름이었다. 문서가 먼저 확정돼 있었기 때문에, 중간에 요구사항이 바뀌어도 코드 전체를 다시 검토하지 않고 해당 문서만 고쳐 재작업 범위를 좁힐 수 있었다고 설명된다.

## 비슷한 것과 비교

| 구분 | 일반 AI 코딩 어시스턴트(채팅형) | Kiro(스펙 기반) |
|---|---|---|
| 작업 방식 | 프롬프트로 묻고 제안을 받아 즉석 반영 | 요구사항·설계 문서를 먼저 확정한 뒤 구현 |
| 강점 | 초기 속도가 빠름, 가벼운 수정에 적합 | 프로젝트가 커져도 의도에서 벗어나기 어려움 |
| 한계 | 프로젝트가 커지면 원래 의도에서 점차 벗어남(프로덕션 드리프트) | 문서 작성에 초기 시간이 더 든다 |
| 언제 쓰나 | 단순 스크립트·일회성 작업 | 여러 사람이 오래 유지보수할 프로젝트 |

선택 기준: 결과물을 오래 유지보수하고 나중에 왜 그렇게 만들었는지 되짚어야 한다면 스펙 기반 개발이, 당장 빠르게 뭔가를 시도해보는 것이 목적이라면 채팅형 방식이 더 맞는다.

## 왜 지금 중요한가

AWS 공식 블로그(devops 블로그)는 Amazon Q Developer 지원 종료 일정을 위 문단의 날짜 그대로 명시하며, 고객에게 Kiro 다운로드와 마이그레이션 가이드 검토를 권고한다.

AWS의 다른 공식 블로그(산업별 블로그)는 Kiro가 "스펙 기반 개발을 중심으로 구축된 첫 AI 코딩 도구"라고 소개하며, 생명과학 분야 고객이 연구·개발 워크플로우부터 상용 운영까지 이 도구로 가속화한 사례를 다룬다. 이 사례에서도 requirements.md→design.md→tasks.md 3단계 흐름이 그대로 확인된다.

핵심은 시장 1위 클라우드 사업자가 자사의 기존 AI 코딩 도구를 접고 "스펙 우선"이라는 방법론 자체를 새 제품의 정체성으로 내세웠다는 점이다. 이는 에이전틱 코딩 업계 전반에서 "빠른 프롬프트 반복"보다 "문서화된 계획 후 실행"이 더 신뢰할 수 있는 방향으로 받아들여지고 있다는 신호로 볼 수 있다.

## 회계법인 AI 직무 연결 포인트

감사 업무는 원래도 절차 문서화가 핵심이다. 감사 계획 단계에서 감사 범위·절차·위험 평가를 먼저 문서로 확정한 뒤 실제 감사 절차를 수행하는 흐름은, Kiro가 요구사항 문서를 먼저 확정한 뒤 코드를 생성하는 흐름과 구조적으로 닮아 있다. 회계법인이 자체적으로 AI 코딩 도구를 도입할 때, 이런 "선(先) 문서화 후(後) 실행" 방식론은 내부통제 관점에서 설명하기 쉬운 장점이 있다.

AI가 만든 산출물(코드든 감사조서든)이 나중에 왜 그렇게 만들어졌는지 추적해야 하는 상황에서, requirements.md·design.md 같은 중간 산출물은 그 자체로 감사증적(audit trail) 역할을 할 수 있다. AI 에이전트가 자동 생성한 자료를 감사인이 검토할 때, "이 결과가 어떤 요구사항·설계 근거로 나왔는가"를 되짚을 수 있는 구조가 있는지는 향후 AI 감사 실무에서 점검 포인트가 될 수 있다.

## 핵심 용어·논쟁

- **EARS(Easy Approach to Requirements Syntax)** — 요구사항을 정해진 문장 패턴으로 적어 모호함을 줄이는 표기법.
- **스펙 기반 개발(Spec-Driven Development)** — 코드 작성 전에 요구사항·설계 문서를 먼저 만들고 그 문서를 기준으로 구현하는 방식.
- **바이브 코딩(Vibe Coding)** — 문서화 없이 프롬프트와 즉석 피드백만으로 코드를 반복 수정하는 방식.
- **프로덕션 드리프트** — AI가 반복 수정한 코드가 원래 의도·요구사항에서 점점 벗어나는 현상.

스펙 기반 개발이 실제로 프로덕션 드리프트를 줄이는지에 대한 독립적인 정량 검증은 아직 충분히 축적되지 않았다. 지금까지 나온 사례는 대부분 AWS 자체 블로그의 고객 사례이며, 제3자 벤치마크는 확인되지 않는다.
