## 상세 내용

영상은 Replit 공식 라이브스트림 "Replit Live"의 한 회차로, 진행자 두 명이 실시간으로 CRM(고객 관리) 앱을 만들어가며 병렬 태스크(parallel task, 곧 리플릿이 부르는 방식의 "포킹") 기능을 실습으로 설명한다. 오프닝에서는 커뮤니티 업데이트를 짧게 다룬 뒤 곧바로 본 주제로 들어간다.

핵심 개념은 "메인 스레드(main thread)"와 "백그라운드 태스크(background task)"의 구분이다. 메인 스레드는 사용자가 프로젝트에 들어갔을 때 기본으로 보는 채팅이며, 여기서 하는 모든 작업은 실시간으로 라이브 코드에 반영된다. 반면 좌측 상단의 "+" 버튼을 눌러 새 태스크를 시작하면, Replit은 프로젝트를 포크한다. 진행자는 이를 전통적인 개발팀의 git 브랜치 워크플로에 비유하면서, "여러 개발자가 큰 코드 더미 하나를 동시에 만지지 않는 것처럼, 병렬 태스크도 각자 독립된 사본에서 작업한다"고 설명한다.

포크의 격리 범위는 코드에만 그치지 않는다. 진행자는 시청자 질문에 답하며 각 포크가 별도의 데이터베이스, 별도의 로그인 세션과 OAuth 토큰까지 갖는다고 밝힌다. 그래서 메인 스레드에서 로그인한 상태여도 새로 만든 포크에서는 다시 로그인해야 하는데, 이는 버그가 아니라 "각 병렬 태스크마다 독립된 개발 환경을 만드는" 설계에 따른 보안 특성이라고 설명한다. 또한 Replit은 내부적으로 자체 버전관리 시스템을 사용하므로, 병렬 태스크를 쓰기 위해 GitHub이나 Bitbucket 같은 외부 git 서비스에 연결할 필요가 없다고 강조한다. 원한다면 나중에 외부 저장소와 동기화할 수도 있다.

태스크보드는 Draft(초안)·Active(진행 중)·Ready(병합 준비 완료)·Done(완료) 네 개 컬럼으로 구성되며, 겉보기엔 칸반 보드 같지만 정확히 칸반처럼 동작하지는 않는다고 진행자는 짚는다. 각 태스크 아이콘은 상태에 따라 회색(대기)·파랑(진행 중, 움직이는 애니메이션)·초록(병합 준비 완료)으로 표시된다. 태스크보드는 좌측 하단에서 접근하며, 팀으로 작업할 때 "누가 어떤 태스크를 큐에 넣었는지" 필터링해 볼 수 있는 기능도 있다고 소개한다.

실습은 이미 만들어 둔 CRM 앱에 새 태스크를 추가하는 것으로 시작한다. 첫 태스크에서 에이전트가 임의로 사이드바를 화면 하단으로 옮기는 결정을 내리자, 진행자는 "탭(tab) 방식으로 바꿔달라"고 추가 지시를 내려 결과를 수정한다. 태스크가 끝나면 화면 하단에 "Ready for review" 알림이 뜨고, 이를 클릭하면 diff(변경 내역) 화면에서 무엇이 바뀌었는지 확인할 수 있다. 마음에 들면 "Apply changes"를 눌러 메인 브랜치로 병합하고, 마음에 들지 않으면 태스크를 그냥 버려도 메인 프로젝트에는 아무 영향이 없다고 설명한다. 병합 전까지 여러 개의 백그라운드 태스크를 동시에 쌓아두고 계속 메인 스레드에서 별도 작업을 이어갈 수 있다는 점도 강조된다.

시청자 질문으로 "병렬 태스크는 크레딧을 어떻게 소모하는가"가 나오자, 진행자는 병렬 태스크도 결국 동일한 Replit 에이전트이며 같은 컨텍스트·같은 비용 구조를 그대로 여러 개 동시에 쓰는 것일 뿐, 별도의 요금 체계가 있는 것은 아니라고 답한다.

이후 진행자는 에이전트가 스스로 제안하는 "Suggested Tasks(제안 태스크)"를 여러 개 한꺼번에 Active 상태로 밀어넣어 실제 병렬 실행을 시연한다. 이 과정에서 실제 충돌 사례가 발생한다. 한 포크는 사이드바 그룹 항목의 색상을 눈에 띄게 바꾸는 작업을, 다른 포크는 같은 사이드바에 그룹별 연락처 수를 보여주는 배지를 추가하는 작업을 동시에 수행했는데, 두 작업이 같은 컴포넌트를 건드리면서 병합 시점에 충돌이 발생했다. 에이전트는 로그에서 "두 변경을 모두 병합한다(merge both directly)"고 판단을 내렸고, 배지 래퍼(badge wrapper)와 읽기 쉬운 배경 텍스트 색상을 함께 유지하는 방식으로 리베이스를 통해 자동으로 충돌을 해소했다. 진행자는 이 장면에서 "리베이스가 뭔지 찾아보고 사람이 직접 리베이스하다 얼마나 고생하는지 살펴보라"며, 이 과정을 에이전트가 대신 처리해주는 게 얼마나 편한지를 강조한다.

제약사항도 여러 차례 짚는다. 첫째, 병렬 태스크(백그라운드 태스크) 안에서는 디자인 캔버스가 읽기 전용으로만 열린다. 포크는 코드는 복제하지만 캔버스나 다른 일부 자산까지 복제하지는 않기 때문이다. 둘째, 앞서 언급한 로그인 세션 분리 문제다. 셋째, 가장 중요한 실전 조언으로 "같은 코드 영역을 여러 병렬 태스크가 동시에 건드리지 않도록 작업을 구획하라"는 점을 반복해서 강조한다. 메인 스레드에서 A 기능을 만들고 있다면, 병렬 태스크는 A와 무관한 B 기능(예: 모바일 앱, 완전히 별도의 기능 확장)에 배정하는 식으로 작업 범위를 나눠야 충돌을 줄일 수 있다고 설명한다. 태스크 사이에 의존 관계가 있으면 위 태스크가 끝날 때까지 아래 태스크가 자동으로 대기하기도 한다.

후반부에서는 CRM 앱을 계속 확장하며 병렬 태스크의 실전 활용을 보여준다. 새로 추가한 연락처에 대해 웹 검색으로 배경 정보를 자동으로 조사해 채워 넣는 "AI 리서치" 기능을 백그라운드 태스크로 돌리고, 파일 업로드가 되지 않는 버그를 발견하자 이를 별도의 새 태스크로 분리해 수정을 맡긴다. 이어 "네이티브 컴패니언 모바일 앱을 만들어달라"는 요청을 또 다른 병렬 태스크로 동시에 진행시키면서, 한 프로젝트 안에서 웹앱·모바일 앱·이미지·프레젠테이션 등 여러 형태의 산출물(멀티 아티팩트)을 동시에 다룰 수 있다는 점을 강조한다.

## 실무 팁 정리

- 병렬 태스크를 시작하려면 메인 스레드 좌측의 "+" 버튼을 누르면 되며, 이는 곧 프로젝트를 포크하는 것과 같다.
- 각 포크는 코드뿐 아니라 데이터베이스와 로그인 세션까지 별도이므로, 포크마다 재로그인이 필요할 수 있다는 점을 미리 알아두어야 한다.
- 병렬 태스크는 Replit 내부 자체 git으로 관리되므로 GitHub 연동 없이도 바로 쓸 수 있다.
- 충돌을 줄이려면 메인 스레드와 병렬 태스크가 서로 다른 코드 영역(다른 기능)을 담당하도록 작업을 나누는 것이 핵심 원칙이다. 같은 컴포넌트를 여러 태스크가 동시에 건드리면 충돌 가능성이 커진다.
- 태스크가 "Ready for review" 상태가 되어도 즉시 병합하지 않고 원하는 시점까지 미뤄둘 수 있으며, 마음에 들지 않으면 그냥 버려도 메인 프로젝트에는 영향이 없다.
- 병렬 태스크 안에서는 디자인 캔버스가 읽기 전용이라는 점, 태스크별로 자동 병합(auto-apply) 옵션을 켤 수 있다는 점도 UI에서 확인할 수 있다.
- 진행자는 병렬 태스크가 Pro·Enterprise 플랜 사용자에게 익숙한 기능이라고 언급했으며, 방송 중 일부 시청자가 이를 계기로 Pro·Enterprise 플랜으로 업그레이드했다는 채팅 반응도 소개됐다(자막 상 정확한 요금제 세부조건은 직접 재확인 필요).
