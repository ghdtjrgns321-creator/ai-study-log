# 오늘의 AI 개념: 에이전틱 브라우저(Agentic Browser)

> 작성일: 2026-08-13 · 분류: ai-concept

## 한 줄 정의

에이전틱 브라우저란 AI가 웹페이지의 구조(DOM)와 로그인 세션을 직접 이해한 채로 클릭·입력·탐색 같은 브라우저 전용 동작을 스스로 판단해 실행하며, 폼 작성·데이터 추출·다단계 웹 작업을 자율적으로 끝까지 수행하는 브라우저 또는 브라우저 자동화 도구를 말한다.

## 쉬운 설명

기존 브라우저는 사람이 주소를 입력하고 버튼을 눌러야 움직이는 수동적인 창이었다. 에이전틱 브라우저는 여기에 목표를 이해하고 판단하는 층을 얹어, "이 상품을 최저가로 사줘" 같은 지시를 받으면 검색·비교·장바구니 담기·결제까지 사람 대신 끝까지 처리한다.

비유하면 기존 브라우저가 운전자가 직접 핸들을 잡아야 하는 자동차라면, 에이전틱 브라우저는 목적지만 말하면 알아서 신호를 보고 차선을 바꾸는 자율주행차에 가깝다. 다만 도로가 아니라 웹페이지의 버튼·입력창·링크가 조작 대상이라는 점이 다르다.

이전에 다룬 컴퓨터 사용 에이전트(Computer Use Agent, 2026-07-10)와는 접근 방식이 다르다. 컴퓨터 사용 에이전트는 화면을 스크린샷으로 찍어 픽셀 단위로 "어디에 무엇이 있는지" 눈으로 보듯 파악하고, 운영체제 전반(데스크톱 앱·파일시스템 포함)을 마우스·키보드로 조작하는 범용 방식이다. 에이전틱 브라우저는 웹이라는 한정된 영역에서 페이지의 DOM·접근성 트리(Accessibility Tree)를 직접 읽어 요소를 식별하고, 로그인 세션·쿠키를 유지한 채로 웹 전용 동작(탐색·폼 제출·다운로드 등)만 수행하도록 특화돼 있다.

## 동작 원리

1. 페이지가 로드되면 에이전트는 원본 HTML을 그대로 읽지 않고, 브라우저가 내부적으로 생성하는 접근성 트리를 우선 활용한다. 접근성 트리는 원래 스크린 리더용으로 만들어진 구조로, 버튼·링크·입력창의 역할(role)·이름(name)·상태(state)만 남기고 나머지 레이아웃 정보를 걷어낸다.
2. isagentready.com의 2026년 3월 분석에 따르면 같은 페이지라도 원본 DOM은 토큰 1만 5000개 이상을 소비하는 반면 접근성 트리는 200~400개 수준이라고 설명한다(해당 블로그 자체 분석 수치이며 학술적 출처는 명시돼 있지 않다). 이 압축된 표현 덕분에 에이전트는 페이지를 통째로 캡처한 스크린샷보다 훨씬 적은 토큰으로 "지금 클릭 가능한 것이 무엇인가"를 파악한다.
3. 에이전트는 이 구조화된 표현과 목표(사용자 지시)를 함께 대형언어모델에 넣어, 다음 행동(클릭·입력·스크롤·탭 전환)을 결정한다. 이 판단은 시각 모델과 결합되기도 하는데, 텍스트 구조만으로 애매한 경우(레이아웃·색상 강조 등) 스크린샷을 보조 신호로 함께 참고한다.
4. 행동을 실행한 뒤 페이지가 바뀌면 위 과정을 반복하며, 이 사이 로그인 세션·쿠키·로컬스토리지는 브라우저 프로필에 그대로 유지돼 매 단계 새로 로그인할 필요가 없다.

## 구체 예시·사례

오픈소스 프레임워크 브라우저 유즈(Browser Use)를 다룬 실습 영상(유튜버 Jesús Copado, 2025-07-30 게시)에서 실제 동작을 확인할 수 있다. 사용자는 원격 디버깅 모드로 자신의 크롬 브라우저를 에이전트에 연결하는데, 이 브라우저는 아마존·챗GPT에 이미 로그인돼 있는 상태였다. 이어 "챗GPT에게 철학자 키르케고르의 입문서를 추천받고, 그 책을 픽업 지점으로 배송받게 아마존에서 구매해줘"라는 지시를 내리자, 에이전트는 챗GPT 페이지를 열어 대화하고 추천받은 책 제목을 그대로 아마존 검색창에 입력해 장바구니에 담고 결제까지 진행했다.

같은 영상에서 실패 사례도 함께 확인된다. 픽업 지점 배송을 요청했지만 해당 상품이 아마존 자체 배송이 아니어서 지정한 장소로 보낼 수 없었는데, 에이전트는 대안을 제안하지 못하고 그 자리에서 멈췄다. 사람에게 "이렇게 바꿔도 될까요"라고 되묻는 인간 개입(human-in-the-loop) 기능이 당시 버전에는 없었다는 한계도 함께 드러났다.

## 왜 지금 중요한가

Firecrawl 블로그(2026년 6월 갱신)는 에이전틱 브라우저 생태계를 AI 지원 소비자 브라우저(Comet·Atlas·Dia·Opera Neon), 오픈소스 에이전트 프레임워크(Browser Use·Stagehand·Skyvern·Agent Browser), 관리형 인프라(Firecrawl·Browserbase·Steel) 세 갈래로 정리하며, Browser Use가 WebVoyager 벤치마크(586개 웹 작업)에서 89.1% 성공률을 기록했다고 전한다(브라우저 유즈 측 발표를 인용한 수치로 독립검증 여부는 확인되지 않는다).

가장 큰 변화는 소비자 브라우저 진영에서 나왔다. 테크크런치(2026-07-09)에 따르면 오픈AI는 출시 9개월도 안 된 챗GPT 아틀라스(Atlas) 브라우저를 2026년 8월 9일부로 단종하고, 그 기능을 챗GPT 데스크톱 앱과 크롬 확장 프로그램으로 옮긴다고 발표했다. "브라우저는 목적지가 아니라 기능"이라는 판단에 따라 별도 브라우저 대신 이미 쓰이는 플랫폼에 에이전트 기능을 심는 방향으로 전략을 바꾼 것이다. 이는 에이전틱 브라우저가 독립 제품보다 기존 브라우저·앱에 스며드는 "기능"으로 재편되고 있음을 보여주는 사례로 꼽힌다.

오픈소스 진영에서는 Browser Use의 깃허브 저장소가 2026년 8월 기준 약 10만 9000개 스타를 보유하고 있으며(저장소 자체 집계), README는 자체 집계한 Odysseys 리더보드에서 오픈AI·앤트로픽·구글·마이크로소프트의 컴퓨터 사용 에이전트를 앞선 87.4% 평균 성공률을 기록했다고 밝히고 있다(벤더 자체 발표 수치).

## 회계법인 AI 직무 연결 포인트

외부조회(External Confirmation) 업무는 은행·거래처 포털에 로그인해 잔액이나 채권채무를 조회하고 회신을 받는 절차가 많아, 에이전틱 브라우저가 반복적인 조회·다운로드 과정을 대신할 여지가 있다. 다만 이런 포털은 대부분 로그인 세션 자체가 통제 대상이므로, 에이전트가 어떤 계정 세션으로 접근했고 어떤 화면을 근거로 값을 읽었는지 단계별로 기록되지 않으면 감사증거로서의 추적 가능성이 떨어진다.

경쟁사·시장 데이터 리서치나 전자공시시스템(DART)·거래소 공시 모니터링에도 적용할 수 있다. 정기 공시나 특정 키워드가 포함된 공시를 여러 페이지에 걸쳐 찾아 요약하는 작업은 사람이 반복하기엔 소모적이지만, 브라우저의 DOM 구조를 그대로 읽는 에이전틱 브라우저에게는 상대적으로 안정적인 작업이다.

동시에 데이터 무결성 리스크를 분명히 인식해야 한다. 에이전틱 브라우저가 읽어온 화면 값은 웹페이지에 삽입된 악성 지시(간접 프롬프트 인젝션)에 의해 조작될 위험이 있고, 값 하나를 잘못 읽어도 사람이 검증하지 않으면 그대로 감사조서에 반영될 수 있다. 자동화된 웹 조회 결과를 감사증거로 채택하려면, 에이전트가 실제로 방문한 화면의 스크린샷·URL·타임스탬프를 남기는 등 사람이 사후 검증할 수 있는 감사증적을 별도로 설계해야 한다.

## 핵심 용어·논쟁

- DOM(Document Object Model) — 웹페이지의 구조를 트리 형태로 표현한 원본 데이터로, 요소 수가 많아 그대로 넣으면 토큰 소모가 크다.
- 접근성 트리(Accessibility Tree) — 브라우저가 DOM에서 역할·이름·상태만 추려 만드는 경량 표현으로, 원래는 스크린 리더용이지만 에이전트의 주요 입력으로도 쓰인다.
- 세션·쿠키 상태(Session/Cookie State) — 로그인 여부·장바구니 내용 등 브라우저에 남는 상태 정보로, 에이전틱 브라우저는 이를 유지한 채 여러 단계를 이어간다.
- 액션 스페이스(Action Space) — 에이전트가 취할 수 있는 행동 집합. 에이전틱 브라우저는 클릭·입력·스크롤·탭 전환·다운로드 등 웹 전용 행동으로 제한된다.
- 간접 프롬프트 인젝션(Indirect Prompt Injection) — 웹페이지 콘텐츠 안에 숨겨진 지시문이 에이전트를 속여 원래 목표와 다른 행동(정보 유출 등)을 하게 만드는 공격.

현재 논쟁거리는 두 가지다. 하나는 벤치마크 신뢰성으로, WebVoyager·Odysseys 같은 수치 대부분이 도구 제작사 자체 발표거나 자체 집계 리더보드에 의존해 독립검증이 부족하다는 지적이 있다. 다른 하나는 보안으로, 로그인 세션을 그대로 넘겨받아 동작하는 구조 특성상 간접 프롬프트 인젝션이 성공하면 컴퓨터 사용 에이전트보다 더 직접적으로 계정·결제 정보에 접근할 수 있어, 인간 개입 단계 없이 자율 결제·자율 제출까지 허용해도 되는지에 대한 합의가 아직 없다.

## 자가 점검 질문

1. 에이전틱 브라우저가 DOM·접근성 트리를 우선 활용하는 방식이, 컴퓨터 사용 에이전트의 스크린샷 기반 방식과 비교해 속도·비용·신뢰성 면에서 각각 어떤 장단점을 만드는가.
2. 회계·감사 업무에 에이전틱 브라우저를 도입한다면, 로그인 세션을 유지한 채 동작한다는 특성이 통제 설계(권한 분리, 접근 로그)에 어떤 요구사항을 추가로 만드는가.
3. 자동화된 웹 조회 결과를 감사증거로 채택하려면, 에이전트가 실제로 무엇을 보고 판단했는지 사후에 검증할 수 있는 감사증적을 구체적으로 어떻게 설계해야 하는가.
