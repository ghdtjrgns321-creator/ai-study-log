## 하위 주제·챕터별 상세 정리

### 1. 도입 — 제작자의 해킹 경험과 영상 제작 배경
제작자 크리스(Chris Raroque)는 10년 이상 iOS·React 개발자로 일해왔으며, 몇 주 전 자신의 생산성 앱이 해킹당한 경험을 공유하는 영상을 올린 뒤 시청자들의 후속 요청을 받아 이 영상을 제작했다고 밝힌다. 이 영상은 "완전한 보안 가이드가 아니라, 특히 AI로 빠르게 만든 앱에서 자신이 직접 목격한 가장 흔한 실수들"을 다룬다고 미리 선을 긋는다.

### 2. 실수 1 — RLS(행 단위 보안) 설정 오류
- 기존 앱 구조는 프런트엔드가 데이터베이스에 직접 접근하지 못하고 반드시 백엔드를 거쳐야 했다. Firebase·Supabase는 이 구조를 깨고 "백엔드 없이도 앱을 만들 수 있다"는 제안과 함께, 프런트엔드가 DB에 직접 통신하는 클라이언트 라이브러리를 제공했다.
- 이 구조의 보안 문제를 보완하기 위해 도입된 것이 RLS(Row-Level Security, Supabase) 또는 Firebase 보안 규칙이다. 이는 "사용자는 자신의 데이터만 읽고 쓸 수 있다"는 식의 필터 역할을 한다.
- Firebase는 과거 기본값을 "완전 개방"으로 두고 개발자에게 나중에 규칙을 설정하라고 경고만 했으나, 해킹 사고가 너무 많아지자 일정 기간 후 자동으로 데이터베이스를 잠그는 정책으로 바꿨다.
- 제작자 본인의 칼로리 트래킹 앱 사례: Supabase RLS를 올바르게 설정해 사용자가 자신의 데이터만 읽고 쓰도록 했다고 확신했고, Claude와 Cursor로도 이중 점검했지만, 구독 상태(subscription status)와 사용량 제한(rate limit) 값을 같은 테이블에 저장한 것이 문제였다. 사용자가 이 값을 직접 수정해 스스로 프리미엄 등급을 부여하고 AI 엔드포인트 사용 제한을 없애 1만 달러 상당의 비용을 발생시킬 수 있었다.
- Claude·Cursor에 "RLS를 점검해달라"고 일반적으로 요청하는 것만으로는 이런 문제를 잡아내지 못했다고 강조한다. "구독 상태를 우회할 수 있는가", "사용량 제한을 조작할 수 있는가", "다른 사용자의 데이터를 읽을 수 있는 시나리오가 있는가" 같은 구체적 시나리오를 프롬프트에 넣어야 한다고 조언한다.
- 영상 준비 과정에서 지인들의 앱(비개발자·개발자 모두 포함)을 직접 감사한 결과, 절반 이상에서 동일한 패턴의 취약점을 발견했다고 밝힌다. 한 사례에서는 사용자 테이블 전체를 다운로드할 수 있었다.
- 가장 흔한 패턴 두 가지: (1) 구독 상태·사용량 제한처럼 민감한 값을 사용자 테이블에 그대로 저장, (2) 다른 사용자의 데이터가 노출되는 RLS 설정 오류.
- Claude Code·Cursor를 쓸 때는 Supabase·Firebase MCP(또는 AWS·Azure CLI)를 직접 연결해 실제 설정을 감사하게 하는 것이 스크린샷·SQL 덤프를 복사해 붙여넣는 것보다 훨씬 낫다고 권장한다.
- (중간에 스폰서 구간: 음성 받아쓰기 도구 WhisperFlow 소개 — 개발 관련 용어 인식과 Cursor·Windsurf 연동 기능 언급.)

### 3. 실수 2 — 요청 빈도 제한(Rate Limit) 부재
- 프런트엔드에서만 "하루 5회 생성"처럼 제한을 걸어도, 공격자가 백엔드 엔드포인트를 직접 찾아내면 이 제한을 우회할 수 있다. 네트워크 탭으로 엔드포인트를 찾는 것은 웹은 물론 모바일 앱에서도 어렵지 않다.
- 해결책은 반드시 백엔드에 제한을 두는 것이며, 사용자별 제한(개별 테이블에 사용량·한도 기록)과 IP 기반 제한을 함께 쓰는 방식을 권장한다. 단, 사용량 제한 값을 사용자가 수정 가능한 테이블에 함께 두면 안 된다는 점(실수 1과 연결)을 다시 강조한다.
- AI 기능이 없는 앱이라도 Firebase·Supabase처럼 사용량 기반 과금 서비스라면, 무제한 요청으로 큰 비용이 청구될 수 있어 이런 제한이 필요하다.

### 4. 실수 3 — 민감한 API를 프런트엔드에서 직접 호출
- Stripe(결제), SendGrid·Postmark(이메일 발송), AWS S3(클라우드 저장소), AI 제공자(예: Vertex AI) 등을 프런트엔드에서 직접 호출하는 경우를 흔히 본다고 지적한다. 이 경우 공격자가 엔드포인트·키를 가로채 가격을 조작하거나, 사용자 명의로 이메일을 발송하거나, 저장소에 임의로 업로드·다운로드하거나, AI 사용량을 임의로 늘려 비용을 발생시킬 수 있다.
- 흔한 오해를 정정한다: 모바일 앱을 포함한 프런트엔드의 환경변수는 "저절로 안전한 것이 아니다." 환경변수는 오직 백엔드에서만 안전하며, 민감한 호출은 반드시 백엔드를 거쳐야 한다.
- 예산 상한(budget cap) 미설정의 위험도 실제 사례로 설명한다. 제작자는 과거 AWS 키가 유출돼 누군가 AWS SageMaker로 머신러닝 학습을 실행해 3만 달러 청구서를 받았던 경험(운 좋게 2000달러로 감면)을 공유하며, 이 사건 이후 예산 상한·환경변수 은닉을 훨씬 진지하게 다루게 됐다고 말한다.

### 5. 핵심 주장 — "바이브 코딩이 본질적으로 안전하지 않은 것은 아니다"
- 자주 받는 질문("바이브 코딩·LLM 코딩은 본질적으로 안전하지 않은가")에 대해 제작자는 "아니다"라고 답한다. 오히려 AI로 코딩한 앱이 과거 손으로 짠 앱보다 더 안전하다고 주장하며, 실제로 옛날 코드베이스에 Claude Code·Cursor를 붙여 여러 취약점을 찾아낸 경험을 근거로 든다.
- 이유로 LLM은 사람이 놓치기 쉬운 엣지 케이스를 더 잘 짚어내고, 사람과 달리 지치지 않는다는 점을 든다. 다만 이는 "무엇이 벌어지는지 이해하고, 통제권을 유지하며, 보안을 의도적으로 신경 쓰는" 바이브 코딩에 한정된 주장이며, 아무 것도 검토하지 않고 그냥 배포하는 방식은 손코딩으로 대충 하는 것과 마찬가지로 취약하다고 선을 긋는다.
- Claude와 "프롬프트 인젝션 시나리오라면 어떨까" 같은 구체적 보안 대화를 나누는 것을 좋아한다며, 이런 대화 자체가 더 안전한 결과로 이어진다고 말한다.

### 6. 마무리 — 무료 체크리스트와 추가 도구
- 영상 설명란에 자신이 만든 무료 마크다운 점검 파일을 공유하며, 이를 Claude Code·Cursor에 붙여넣어 코드베이스를 감사하게 해보라고 권한다.
- 자신이 만든 내부 도구(코드베이스 접근 없이도 펜테스터처럼 앱을 공격해보는 에이전트)를 언급하며, 공개 여부는 시청자 반응에 달려 있다고 밝힌다(이 영상 시점 기준 미공개 대기자 명단 운영).

## 실무 팁 요약(원문 보존)

- RLS·보안 규칙을 점검할 때는 "구독 상태를 우회할 수 있는가", "사용량 제한을 조작할 수 있는가", "다른 사용자 데이터를 읽을 수 있는가"처럼 구체적 시나리오로 프롬프트할 것.
- 구독 상태·사용량 제한처럼 민감한 값은 사용자가 쓰기 권한을 가진 테이블과 분리해 저장할 것.
- 프런트엔드 제한만으로는 부족하므로 반드시 백엔드·IP 기반 요청 제한을 함께 둘 것.
- Stripe·이메일 서비스·클라우드 저장소·AI 제공자 호출은 반드시 백엔드를 경유하고, 프런트엔드 환경변수에 민감 정보를 두지 말 것.
- 모든 유료 서비스에 예산 상한을 설정하고, 상한이 없는 서비스는 최소한 임계치 알림이라도 설정할 것.
- Claude Code·Cursor를 쓸 때는 Supabase·Firebase MCP(또는 클라우드 CLI)를 직접 연결해 실제 설정을 감사하게 할 것.

## 직접 재확인이 필요한 부분

- "지인 앱의 절반 이상에서 동일 취약점을 발견했다"는 수치는 제작자의 소규모 자체 감사(표본 수 비공개) 결과로, 통계적으로 검증된 수치가 아니다.
- Firebase·Supabase의 기본 보안 규칙 정책(자동 잠금 등)은 영상 게시 시점(2026-03-16) 기준 설명이며, 현재 정책은 공식 문서에서 별도로 재확인이 필요하다.
- 제작자가 언급한 "펜테스터형 내부 도구"의 공개 여부는 이 영상만으로는 확인되지 않는다.
