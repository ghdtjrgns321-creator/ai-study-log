## 다루는 하위 주제 순서

### 1. 도입 — 이번 주 최대 발표, 클라우드 에이전트
- 진행자가 "이번 주 Cursor 최대 발표는 클라우드 에이전트"라며, "에이전트에게 컴퓨터를 통째로 준다"는 방향성으로 이번 업데이트를 소개한다.
- 예전 클라우드 에이전트는 자기만의 컴퓨터에서 돌긴 했지만 코드를 읽고 쓰기만 하는 "텅 빈 VM"이었고, 해당 레포에 맞는 개발 환경(DevX)이 세팅돼 있지 않았다는 점을 짚는다.
- 모델 입장에서 토큰만 흘려보내고 결과가 맞는지 확인할 방법이 없었다면 성능이 나쁠 수밖에 없다는 비유를 들며, "모델에게 직접 코드를 실행해볼 수단을 주는 것"이 이번 업데이트의 핵심이라고 설명한다.

### 2. 데모 — cursor.com/agents 화면 시연
- 왼쪽에는 일반적인 채팅 UI가 있고, 가장 큰 변화는 "에이전트가 자신의 변경사항을 직접 테스트한다"는 점이다.
- 예시로 든 작업은 30분이 걸렸는데, 코드를 쓰는 시간뿐 아니라 처음부터 끝까지(dev 서버 기동, 반복 테스트) 실제로 검증하는 시간이 포함됐기 때문이라고 설명한다.
- "다 해봤다"는 PR이 아니라 "직접 테스트해서 준비됐다"는 PR을 받는 것이 목표라며, 사람이 리뷰 요청을 받았는데 상대가 테스트도 안 해봤다면 짜증나는 것과 같은 논리라고 비유한다.
- 아주 단순한 카피 변경 같은 작업은 테스트를 건너뛰기도 하며, `/no-test` 슬래시 커맨드로 사람이 직접 테스트를 끌 수도 있다. 기본값은 "단순 변경은 스킵, 복잡한 변경은 테스트"로 캘리브레이션돼 있고, `agents.md` 파일에 특정 서브 디렉터리는 테스트 불가능하다고 지정해둘 수도 있다.

### 3. 3대 축 — 자체 테스트, 데모 영상, 원격 제어
- **축 1**: 모델이 실제로 변경사항을 테스트한다.
- **축 2**: 모델이 작업 결과를 담은 데모 영상을 만든다. 코드 리뷰 자체를 대체하진 않지만, 거대한 diff를 바로 들여다보는 것보다 훨씬 진입장벽이 낮은 시작점이라고 설명한다. 때로는 스토리북(Storybook) 형태의 컴포넌트 갤러리를 만들기도 한다.
- **축 3**: 사람이 VNC 방식 원격 데스크톱으로 그 VM에 직접 접속해 마우스·키보드로 조작할 수 있다. "영상 하나로 충분할 때도 있지만, 영상이 완벽하지 않을 때는 이 VM에 들어가 직접 눌러보며 반복 요청을 이어간다"고 설명한다.
- 다른 출연자는 "요청이 불충분하게 명시된(underspecification) 문제"를 영상이 완화해준다고 덧붙인다 — 사람이 말로 설명한 "토글이어야 한다"는 요구가 실제로는 체크박스로 구현됐을 때, 로컬에서 브랜치를 받아 실행해보지 않고도 영상만으로 바로 확인할 수 있어 정렬(alignment)에 유용하다는 것이다.

### 4. 프런트엔드에 국한되지 않는다는 점 — 시크릿 저장 오류 메시지 개선 사례
- "이 기능은 프런트엔드에만 해당하나?"라는 질문에 답하기 위한 사례로, 시크릿(secret) 저장 시 오류 메시지 개선 작업을 보여준다.
- 클라우드 에이전트는 시크릿을 추가로 지원하며, 이는 에이전트가 특정 시스템에 접근하기 위한 온보딩 과정의 일부다.
- 시크릿이 너무 크면 저장이 실패하는데 기존 오류 메시지가 "저장 실패"라는 일반적인 메시지뿐이었던 문제를, 에이전트가 별도 지시 없이 브라우저 개발자도구(DevTools)를 열어 자바스크립트로 5,000자짜리 문자를 입력창에 붙여넣고 저장을 눌러 한도 초과를 재현했다.
- 이 사례는 "에이전트가 자신의 클라우드 에이전트를 사용해 클라우드 에이전트 기능을 개선한다"는 메타적인 상황이기도 하다(다만 무한 재귀를 막기 위해 에이전트가 자신의 클라우드 에이전트를 추가로 실행시키는 것은 현재 비활성화돼 있다고 밝힌다).

### 5. 배경 — 오토탭(Autotab)의 교훈과 "브레인 인 어 박스" 철학
- 이런 접근은 2023년(발언 중 정정: 2022년이 아니라 2023년) 시작한 "오토탭" 실험에서 얻은 교훈에서 비롯됐다고 설명한다. 당시는 브라우저 사용, DOM 조작 등 다양한 방식을 시도했다.
- 결국 "모델에게 픽셀과 박스를 그대로 주는 것"이 맞다는 결론(농담 삼아 "AGI-필드"라고 표현)에 이르렀고, 컨텍스트와 능력의 한계를 최대한 없애 모델의 지능 자체가 병목이 되도록 만드는 것이 목표라고 설명한다.
- 사람이 하듯 DevX가 세팅된 VM을 통째로 주는 것이 내부적으로 "이런 종류의 새로운 에이전틱 워크플로우로의 큰 도약"이었다고 강조한다.
- Opus 4.5/4.6과 Codex 5.3 같은 최근 모델들이 "자율성 등급(autonomy grade)" 능력에서 추가적인 단계 변화(step change)를 가져왔다고 언급한다.

### 6. 슬래시 커맨드 투어
- `/no-test` — 테스트를 건너뛰게 하는 커맨드.
- `/repro` — 버그에 대해 먼저 재현 영상을 찍고, 수정 후 재현되지 않음을 보여주는 영상을 다시 찍는 패턴. 이 방식이 매우 유용해 별도 슬래시 커맨드로 만들었다고 설명하며, 이런 유형의 버그는 예전에는 로컬에서 재현하는 데만 오랜 시간이 걸렸지만 이제는 약 90초 만에 확신을 갖고 병합할 수 있게 됐다고 강조한다.
- 이 워크플로우는 머신러닝의 "보상 해킹(reward hacking)" 문제와도 연결된다고 짚는다 — 테스트를 먼저 실패하게 만들고 그다음 통과시키는 건 고전적인 TDD(테스트 주도 개발)의 red-green 패턴과 같다는 지적이 나온다.
- `Fix BB`(Bugbot 자동 수정) — Bugbot이 남긴 코멘트를 원래 PR을 만든 에이전트의 맥락(원본 프롬프트 등)을 활용해 고치는 내부용 커맨드. 최근 "Bugbot Autofix" 기능도 정식 출시했다고 언급한다.
- `Cloud agent diagnosis` — Datadog MCP를 활용해 클라우드 에이전트에 문제가 생겼을 때 서브에이전트 여러 개를 띄워 로그를 탐색하고 원인을 찾는 커맨드. 이와 함께 클라우드 에이전트용 MCP 지원을 이번 출시와 함께 시작했다고 밝힌다(정식 마케팅은 다음 주 예정이라고 언급).
- 트랜스크립트 기반 디버깅 — 한 에이전트의 실행 트랜스크립트를 다른 에이전트에게 넘겨 외부 디버거처럼 활용하거나, 대화를 이어가듯 포크(fork)할 수 있는 기능도 내부적으로 실험 중이며 곧 공개될 예정이라고 밝힌다.

### 7. 출시 타임라인과 지표
- 클라우드 에이전트 자체는 "작년 6월"(2025년 6월)에 처음 출시됐으며, 서서히 발전해온 기능이라고 설명한다.
- 내부적으로 "에이전트가 탭(자동완성)을 추월하는 차트"를 만들어 공유한 적이 있으며, 이를 "코딩 역사상 가장 큰 전환"이라고 표현한다.
- 안드레 카파시(Andrej Karpathy, 발언 중 "Andre Kapathy"로 언급)가 최근 이 흐름을 조명했다고 언급한다.

### 8. 개발의 성격 변화 — 개인 작업에서 협업 중심으로
- Slack이 사실상 "IDE"가 됐다는 표현이 나온다 — 이슈 채널이나 제품 논의 채널에서 사람들이 `@cursor`로 언급하면 클라우드 에이전트가 실행되고, 팀 팔로우업 기능을 켜두면 다른 사람이 스레드에 이어서 맥락을 더할 수 있다.
- 에이전트가 Slack에서 관련 있는 다른 사람을 태그(예: `git blame` 결과를 보고 담당자를 태그)할 수도 있다.
- 다른 출연자는 개발자뿐 아니라 디자이너·세일즈 담당자도 같은 방식으로 협업하고 있다고 언급한다 — 사람들이 나누는 대화의 본질이 "이 if문을 어디에 넣을지" 같은 세부사항이 아니라 "이걸 배포할지, UX가 맞는지" 같은 상위 판단으로 바뀌었다는 점을 강조한다.
- 다만 "뮤트(mute) 버튼이 필요하다"는 언급도 나온다 — 사람들끼리 먼저 논의해야 할 때 에이전트가 계속 끼어들지 않도록, 명시적으로 `@` 멘션할 때만 응답하도록 설계했다고 밝힌다.

### 9. 새로운 병목 — 프로덕션 반영과 코드 리뷰
- 코드를 생성하는 것 자체는 쉬워졌지만, 이를 실제 프로덕션에 반영하는 것은 여전히 상대적으로 어렵다는 "PR은 있는데 머지할 준비는 안 된" 상황을 내부 농담으로 소개한다.
- 리뷰에 대한 두 관점이 소개된다 — "AI가 AI를 리뷰해야 한다"는 입장과 "리뷰는 죽었다, 영상만 보면 된다"는 입장이 공존한다고 언급하며, 발표자 개인은 영상은 정렬(alignment) 확인용으로 쓰고 여전히 코드도 직접 본다고 밝힌다.
- Bugbot에 대한 신뢰가 높아 "Bugbot 코멘트를 무시하지 말라"고 내부적으로 강조하며, 실제로 무시했다가 나중에 버그가 발견된 경험을 반복하면서 팀이 Bugbot을 신뢰하게 됐다고 설명한다.
- 코드 수준 리뷰 외에 기능 수준 리뷰, 향후에는 성능·보안 리뷰 같은 새로운 리뷰 계층이 필요해질 것이라 전망한다.
- 10인 스타트업이 1만 명 기업 수준의 개발 파이프라인(단계적 릴리스, 체크포인트, 자동 회귀 감지, 스택 디프, 머지 큐 등)이 필요해진다는 비유가 나온다. 다만 대다수 사람은 아직 "스택 디프(stacked diffs)"가 뭔지도 모른다는 지적과 함께, 이런 대규모 조직의 관행이 소규모 팀에도 "민주화"되고 있다는 해석을 덧붙인다.

### 10. 기술적 세부사항 Q&A
- VM 크기를 선택할 수 있냐는 질문에 "아직 안 된다, 추가할 계획"이라고 답한다(AWS EC2처럼 인스턴스 크기를 고르는 방식에 비유).
- VM은 "브레인 인 어 박스(brain in a box)"를 지향하며, 완전히 무상태(stateless)가 아니라 어느 정도 지속성(persistence)을 갖도록 설계했다 — 며칠 뒤에도 돌아왔을 때 이전 작업 상태(예: 열려 있던 브라우저 탭)를 그대로 복원할 수 있는 "최대 절전(hibernate)" 방식의 메모리 스냅샷을 지원한다.
- VM 구성 방식은 두 가지다 — Docker파일 기반 설정과, 설치 커맨드 실행 후 파일시스템 전체를 스냅샷하는 리눅스 VM 스냅샷 방식(기본값).
- 데모 영상에서 왜 데스크톱·브라우저를 다 보여주냐는 질문에는, 프런트엔드 작업만 시연하는 게 아니라 팬·줌 같은 편집 기능도 있고, 여러 버전을 시도하다 절반 정도의 기능은 "언십(unship, 배포 취소)"했다고 밝힌다.
- 언십한 두 가지 사례: (1) 로컬 브라우저에서 포트 포워딩으로 VM 내 localhost에 바로 접속하던 네이티브 브라우저 기능은, 원격 데스크톱 방식이 충분히 저지연이고 더 범용적이라 판단해 없앴다. (2) VM 내 파일을 직접 보고 편집할 수 있는 "파일 앱"도 한때 있었지만, 이를 제한함으로써 사용자가 자연스럽게 더 많은 것을 에이전트에게 위임하는 패턴에 익숙해지도록 의도적으로 없앴다고 설명한다. (OpenAI Codex 앱이 파일 편집기가 없어 비판받았던 사례와 비교하며, Cursor는 "지금은 신뢰해달라"는 입장이라고 언급한다.)

### 11. 미래 전망 — 배포 인프라, 모델 선택, 병렬화
- 라이벌인 Lovable·Bolt 같은 "제로투원(0-to-1)" 풀스택 서비스와 달리, Cursor는 배포 인프라(Vercel 같은) 자체를 소유하지 않고 있으며, 당장은 그 방향으로 갈 계획이 없다고 밝힌다 — 이미 Datadog MCP 같은 외부 도구가 있는 상황에서 호스팅 솔루션을 만드는 게 최선이 아니라고 판단한다는 설명이다.
- 모델 선택 UI에 대해서는, 모델 성능 순위가 워낙 자주 바뀌다 보니(Opus 4.5 지지자였다가 Codex 5.3으로 옮겼다는 개인 경험 언급) "Cursor Auto"처럼 상황에 맞는 모델을 자동으로 골라주는 라우팅 기본값을 점점 더 강조하는 방향으로 가고 있다고 설명한다(Auto는 무료가 아니며 별도 요금제가 있음).
- **베스트오브엔(Best-of-N)**과 **패러렐 에이전트(Parallel agents)**의 차이를 정의한다 — 베스트오브엔은 같은 프롬프트로 여러 모델을 동시에 돌리는, 패러렐 에이전트의 부분집합이다. 실제 데모에서 5개 모델에 동일한 프롬프트(Cursor 2.0 클론 만들기)를 동시에 돌리는 화면을 보여준다.
- 로컬 환경에서는 여러 작업을 병렬로 돌릴 때 Git worktree를 쓰는 게 일반적이었지만, "아무도 worktree가 뭔지 모른다"는 지적과 함께 이를 점차 페이즈아웃하고 있다고 밝힌다.
- 서로 다른 모델 제공사의 결과를 종합해 더 나은 diff를 새로 작성하는 "LM 판정 + 코드 작성" 실험(작년에 시도했다가 출시하지 않음)도 언급하며, 서로 다른 모델 제공사를 섞을 때 시너지가 있었다는 학습 내용을 공유한다. 이런 아이디어는 안드레 카파시가 "카운슬(council)"이라 부른 개념과 유사하며, Cursor 내부에는 `/council`이라는 실험적 커맨드도 있다고 밝힌다.

### 12. 서브에이전트와 롱러닝 에이전트(그라인드 모드)
- **서브에이전트(sub agents)**는 서로 다른 프롬프트·목표·모델·버전을 가진 에이전트들이 협업·위임하는 또 다른 방식이라고 소개한다.
- 서브에이전트는 (1) 긴 실행 스레드의 컨텍스트 관리, (2) 특정 작업에 더 많은 컴퓨트를 투입하는 용도로 쓰인다고 설명한다. 예를 들어 "내 코드베이스를 탐색해줘"라고 하면 메인 에이전트가 탐색용 서브에이전트 하나 또는 여러 개를 띄울 수 있다.
- 내장 서브에이전트 예시로 "탐색(explore) 서브에이전트"(빠른 모델로 스마트 라우팅)와 "컴퓨터 사용(computer use) 서브에이전트"(클라우드 에이전트의 테스트·검증 과정에서 이미지가 많이 오가는 긴 궤적을 전담)를 든다.
- 서브에이전트를 쓰는 또 다른 이유는 컨텍스트 압축이다 — 서브에이전트 수준에서 실행 과정을 요약해 최종 메시지 하나로 압축한 뒤 부모 에이전트에게 전달하면, 전역 압축(global compaction) 같은 별도 처리 없이도 자연스러운 압축 경계가 생긴다고 설명한다.
- **그라인드 모드(grind mode)** — 내부적으로 이렇게 부르는 장시간 실행 모드로, "완료 기준을 충족할 때까지 멈추지 않는" 방식이다. 실행 전 계획 단계에서 사람과 정렬(align)하는 과정을 거친 뒤에야 그라인드 실행 단계로 들어간다. 실제로 며칠(최대 3일까지 언급)씩 걸리는 작업도 있어, 장시간 작업을 맡기기 전에는 몇 시간을 들여서라도 요구사항을 명확히 소통해야 한다고 강조한다. 이는 사내에서 브라우저·운영체제를 통째로 만들어보는 실험(여러 워커·플래너 에이전트가 협업하는 "소사이어티" 형태) 과정에서 파생된 기능이라고 소개한다.

### 13. 인프라·규모의 함의
- 클라우드 에이전트로 병렬성이 커지면서 "레이턴시-스루풋 트레이드오프"가 회사의 핵심 멘탈모델이 됐다고 설명한다 — 코드를 파이프를 흐르는 물에 비유하며, 모델 자체가 더 빨라지는 것(유량 증가)과 파이프를 넓히는 것(병렬화, 에이전트 스웜) 둘 다 처리량을 늘리는 데 기여한다고 설명한다.
- 에이전트가 너무 많이 코드를 생성·푸시하면서 실제로 사내 GitHub Actions가 과부하로 멈춘 사례도 있었다고 언급하며, CI/CD 같은 기존 시스템들이 "인력을 10배로 늘린 것과 같은" 부하 증가에 적응해야 한다고 짚는다.
- 강화학습(RL) 인프라를 다루는 리서처들이 겪는 "병렬 롤아웃 스케줄링" 문제와 본질적으로 같은 문제라는 비유도 나온다.
- 개발자 1인당 필요한 추론(inference) 총량이 매우 커지고 있으며, 가장 낙관적인 데이터센터 증설 전망조차 이런 "에이전트 스웜" 규모의 수요를 과소평가하고 있을 수 있다는 의견이 나온다.
- 토큰 소비량에 대한 구체적 수치는 밝히지 않지만, "요금제가 월 20달러(1세대 자동완성) → 월 수백 달러(2세대 로컬 반복) → 앞으로는 월 수천, 잠재적으로 수만 달러 규모"로 이어질 것이라는 전망이 나온다. 이는 제번스의 역설(Jevons paradox, 효율이 오를수록 총 사용량이 늘어나는 현상)이 계속될 것이라는 예상과 함께 언급된다.

### 14. 채용, 예측, 마무리
- 채용 관련해서는 "최신 AI 코딩 기법에 능한 것 자체가 필수조건은 아니다"라면서도, 이를 잘 다루는 사람은 최근 3개월 새 바뀐 게임의 규칙에 빠르게 적응하는 호기심·학습 의지가 있다는 신호로 본다고 설명한다. 여전히 시스템을 설계해본 경험, 좋은 패턴을 알아보는 안목은 중요하다고 강조한다.
- 스레드 간 빠른 전환(context switching) 문제를 다루는 데모도 보여준다 — 아침에 10개 에이전트를 동시에 띄워두고, 하나씩 돌아가며 영상 확인·후속 지시·머지를 반복하는 워크플로우가 로컬 환경의 "어느 work tree였는지 기억 안 남" 문제를 해결해준다고 설명한다.
- 예측 코너에서 한 출연자는 "연말까지 클라우드/에이전트가 자체 VM에서 작업하는 비중이 로컬 에이전트의 2배 이상이 될 것"이라 예측한다.
- 아직 부족한 부분으로는 온보딩(cursor.com/onboard) 자체의 속도와 안정성, 그리고 에이전트의 "기억(memory)" 부재를 꼽는다 — 코드베이스의 설계 트레이드오프, 특정 프로젝트만의 관례(quirk) 같은 것을 계속 학습·유지하는 능력이 다음 단계 도약이 될 것이라 전망한다. 관련해 "다이나믹 파일 컨텍스트"에 대한 사내 블로그 게시물이 언급되며, 메모리를 "에이전트 자기 감사가능성(self-auditability)"의 하위 개념으로 보는 새로운 관점도 소개한다 — 에이전트가 스스로 자신의 하네스(harness)에 빈틈을 발견하면 그에 대한 메모·주석을 스스로 제안할 수 있어야 한다는 것이다.
- 음성 코딩에 대한 짧은 논의도 나온다 — 오토탭 시절 사람들이 부자연스럽게 또박또박 말하려던 습관 때문에 학습이 어려웠던 경험을 공유하며, 아직은 감정적 동반자 역할에 머물러 있지만 언젠가 음성 코딩도 본격화될 것이라 전망한다.
- 마지막으로 "레드카펫이 깔린 것도 아닌데 리트코드(LeetCode) 시대는 끝났다"는 채용 관련 언급과 함께 인터뷰를 마친다.

## 실무 팁·수치 관련 유의사항
- "클라우드 에이전트 최초 출시가 2025년 6월"이라는 발언, "PR 상당수를 이미 에이전트가 작성" 같은 구체적 비율은 영상 내 구두 언급으로, 공식 수치 자료로 별도 확인된 것은 아니므로 재확인이 필요하다.
- "월 수천~수만 달러 규모의 요금제로 이어질 것"이라는 전망은 발화자 개인 의견이며 Cursor의 공식 가격 정책 발표가 아니다.
- VM 크기 선택 기능은 영상 시점(2026-03) 기준 "아직 지원하지 않음, 추가 예정"이었다 — 2026년 8월 현재 실제 지원 여부는 별도 확인이 필요하다.
- 자동 생성 자막 특성상 화자(Sam Whitmore/Jonas Nelle/진행자) 구분이 완벽하지 않을 수 있어, 발언자 귀속은 맥락으로 추정한 부분이 있다.
