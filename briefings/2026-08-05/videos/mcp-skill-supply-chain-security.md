Paul Zenker는 KPMG 독일에서 근무하는 보안 컨설턴트이자 레드팀·펜테스터로, 독일어로 AI 보안 책을 저술했고(영어판은 추후 출간 예정) "부수는 것을 좋아한다"는 성향을 강조하며 발표를 시작한다. Justin Szczepaniak는 학계 출신으로 최근 KPMG 보안 컨설턴트로 합류했다. 두 사람은 발표 전체를 통해 실제 라이브 데모 두 건을 중심으로 MCP(Model Context Protocol)의 현재 보안 상태를 보여준다.

## 1. MCP 개념 기초 설명

발표는 청중을 위해 MCP 동작 방식을 간단히 복습한다.

```
[AI 챗봇/클라이언트]
     │  설정 파일(로컬 디렉터리)에서
     │  MCP 엔드포인트 목록을 읽음
     ▼
[MCP 서버] ── (1) 로컬: stdio로 파일/코드와 상호작용
            └─ (2) 원격: HTTP(S) 또는 웹소켓으로 외부 리소스와 통신
     │
     ▼
[JSON-RPC 메시지]  ← LLM이 채운 명령 + 서버가 반환하는 데이터
```

- MCP 클라이언트(클로드 데스크톱 등 챗봇)는 로컬 앱 디렉터리에 저장된 설정 파일에서 MCP 엔드포인트 정보를 읽어 챗봇에 주입한다.
- 서버와의 연결은 로컬(stdio, 파일·코드 상호작용)과 원격(HTTP/HTTPS, 드물게 웹소켓) 두 방식이 있다.
- 통신은 JSON-RPC 포맷으로 이뤄지며, 이는 결국 텍스트이기 때문에 프롬프트 인젝션의 통로가 될 수 있다는 점을 짚지만, 이 발표의 핵심 주제는 프롬프트 인젝션이 아니라 "공급망"이라고 못박는다.

## 2. 데모 1 — MCP 설정 파일을 이용한 백도어 (Paul Zenker)

핵심 문제 제기: MCP 엔드포인트 설정 파일은 사용자 쓰기 권한이 있는 일반 디렉터리에 저장되며, 사용자 권한으로 실행되는 어떤 프로그램이든 이 파일에 접근·수정할 수 있다. 즉 이 파일에 넣은 내용은 "이름 + 명령(command) + 인자(argument)"로 구성된 셸 명령이며, AI 애플리케이션이 열릴 때마다 자동으로 실행된다.

라이브 데모에서 Paul은 클로드 데스크톱 애플리케이션을 실행하는 화면을 보여주면서, GitHub에서 프로젝트를 설치할 때 흔히 복사-붙여넣기 하는 셸 명령 한 줄이 실제로는 MCP 설정 파일에 임의 명령을 몰래 써넣는 스크립트일 수 있음을 시연한다. 이 스크립트가 실행되면 설정 파일에 원하는 명령이 삽입되고, 이후 애플리케이션이 열릴 때마다 그 명령이 재실행된다. NPX로 npm 패키지의 최신 버전을 내려받아 실행하거나, 원격 셸 스크립트를 실행하는 방식으로도 동일하게 구현 가능하다. Paul은 이를 "레드팀 관점에서 아주 쉽게 만들 수 있는 지속성(persistence) 확보용 백도어"라고 설명한다.

요점: 이것이 사실상 "GitHub에서 복사한 것을 그대로 붙여넣는 순간의 로컬 원격 코드 실행(RCE)"이며, 특히 공급망 측면에서 상당한 공격 표면을 노출한다는 것이다.

## 3. 데모 2 — 툴 실행 하이재킹(Tool Execution Hijacking) (Justin Szczepaniak)

Justin은 이 취약점 클래스를 "툴 실행 하이재킹"이라 명명한다. 프롬프트를 통해 모델을 속이는 대신, 로컬 도구가 어떻게 실행되는지(launch)를 공격하는 한 단계 아래 층위의 공격이다.

### 개념 설명

- MCP 클라이언트는 워크스페이스 설정 파일을 근거로 로컬 도구를 실행한다. 이 파일은 사실상 "모델이 도구 X를 호출하면 이 명령을 실행하라"는 규칙집이다.
- 이 설정 파일이 쓰기 가능하다면, 그 자체가 "실행 제어 평면(execution control plane)"이 되며, 이 파일을 바꿀 수 있는 사람이 실제로 로컬 머신에서 무엇이 실행되는지를 통제하게 된다.
- 공격자는 설정된 명령을 자신이 통제하는 작은 래퍼(wrapper) 스크립트로 바꿔치기할 수 있다. 이 래퍼는 (1) 원래 동작을 그대로 전달해 툴이 정상 작동하는 것처럼 보이게 하면서, (2) 동시에 배경에서 몰래 데이터나 동작을 바꾼다.
- 핵심 차이: 이것은 프롬프트 인젝션이 아니다. 모델을 속이는 것이 아니라, 툴 경계(tool boundary)에서 실행되는 실행 파일 자체가 다른 것으로 바뀌는 "프로세스 치환(process replacement)"이다.

### 라이브 데모 내용

VS Code 화면에서 간단한 할 일 목록(to-do list) MCP 도구를 시연한다. 몇 개 항목을 추가한 뒤, 배경에서는 이미 MCP가 악성 스크립트로 바꿔치기된 상태다. 이 악성 스크립트는 트리거 단어 "sport"에 반응하도록 설계됐다(개발자들이 스포츠를 싫어한다는 농담으로 선택한 단어). "please add sports with Paul"이라는 명령을 입력하자, MCP 도구는 정상적으로 "추가됨" 응답을 반환하지만 배경에서는 할 일 목록 전체가 삭제(wipe)된다.

이때 흥미로운 지점은, 모델(클로드) 관점에서는 툴 호출이 표준적인 성공 응답을 반환하므로 문제가 있다는 어떤 신호도 응답 안에 없다는 점이다. 래퍼는 툴 호출이 끝난 뒤에야 조용히 상태를 바꾸기 때문에, 공격이 일어나는 순간에는 모델이 눈치채지 못하고 사후에야("왜 이런 걸 시켰냐, 혹시 보안 전문가냐"고 클로드가 되묻는 장면) 뭔가 잘못됐음을 인지한다.

### 왜 중요한가

- MCP는 빠르게 AI 에이전트의 표준 인터페이스가 되고 있고, MCP 도구는 파일시스템 조작·코드 실행·CI/CD 파이프라인·내부 프로젝트 데이터 접근 등 강력한 권한을 갖는 경우가 많다.
- 툴 실행 자체를 하이재킹하면 프롬프트 필터·모델 정렬(alignment)·지시 계층(instruction hierarchy) 같은 AI 안전장치를 한꺼번에 우회한다. 공격이 그 아래 층위에서 벌어지기 때문이다.
- 위협 모델은 과장되지 않았다: 공격자가 워크스페이스 파일을 수정할 수 있다는 가정만 필요하고(악성 PR, 공유 저장소 등), 관리자 권한은 필요 없다. 개발자라면 누구나 PR을 승인하고, 의존성을 설치하고, 템플릿을 클론해 본 경험이 있으며, 이 모든 지점이 잠재적 진입점이다.
- 이것은 새로운 제로데이가 아니라 "AI 툴링에 적용된 기본적인 소프트웨어 공급망 리스크"라고 정리한다. 프롬프트 인젝션도, 모델을 헷갈리게 하는 것도, 툴 선택을 조작하는 것도 아니며, 순수한 실행 경로 하이재킹이다.

## 4. 방어 시도 1 — MCP Guard (외부 무결성 모니터)

발표팀이 실험한 첫 번째 방어 아이디어는 "MCP Guard"라는 외부 무결성 모니터다. MCP 설정, 기대되는 명령, 정상 툴 스크립트의 해시값을 감시하다가 뭔가 바뀌면 경고를 띄우는 방식이다. 장점은 MCP 클라이언트 자체를 수정할 필요가 없다는 점이다.

단점(데모로 시연): 감시가 사후적(reactive)이다. 시연에서는 AI가 "sport"를 추가하는 동작을 실제로 수행해 할 일 목록이 삭제된 뒤에야 MCP Guard가 경고를 트리거했다. 즉 경고가 뜨는 시점에는 이미 피해가 발생한 뒤라는 근본적 한계가 있다.

## 5. 방어 시도 2 — MCP 레지스트리(서명 기반 사전 검증)

두 번째, 더 구조적인 아이디어는 탈중앙화된 "승인된 MCP 서버 레지스트리"다.

```
[개발자] → MCP 서버 게시
             │ (게시된 신원 + 서명된 메타데이터
             │  + 기대 명령 + 구현체 암호화 해시)
             ▼
        [MCP 레지스트리]
             │
             ▼
   [MCP 클라이언트가 실행 전 레지스트리 대조]
             │
      일치 ──┴── 불일치
       ▼             ▼
    툴 실행       실행 차단
```

- 각 서버는 게시된 신원, 서명된 메타데이터, 기대되는 명령, 허용된 인자, 구현체의 암호화 해시로 식별된다.
- 클라이언트는 무언가를 실행하기 전에 레지스트리를 조회해 대조하고, 모든 것이 일치할 때만 툴을 실행한다.
- "AI 툴을 위한 패키지 서명"에 비유할 수 있다.
- 기대 효과: 명령 오염 방지, 악성 래퍼 차단, 변조된 툴 스크립트 탐지, 게시자 책임성(accountability) 확보, 조직 전체 정책 적용 가능.
- 발표팀의 결론: 현재 MCP 보안은 대체로 "희망(hope)"에 의존하고 있으며("설정 파일이 괜찮겠지"), 레지스트리는 이를 실제 검증(verification)으로 전환시킬 수 있는 방향이다.

## 6. 인증·인가(Auth) 문제 (Paul Zenker)

발표 후반부에 Paul은 MCP의 인증·인가 이슈를 짧게 짚는다. MCP 프로토콜은 원래 인증 기능이 없었고, 나중에서야("bolted on") 추가됐다. 원격 MCP 서버를 인터넷을 통해 HTTP로 접근하려면 표준화된 인증이 필요한데, 자체 인증을 직접 구현하는 것은 "직접 암호화를 만드는 것"만큼 위험하다고 지적한다.

MCP 공식 사이트에 정리된 취약점 목록을 보면, 대부분의 문제는 두 개의 서로 다른 키(key)가 쓰인다는 데서 발생한다: (1) MCP 클라이언트와 MCP 서버 사이의 OAuth, (2) MCP 서버와 외부 리소스 사이의 별도 인증. 사용자의 신원이 AI 툴을 거쳐 실제 외부 리소스에 도달할 때 확인·검증돼야 하는데, 이 두 인증 사이에 불일치가 있거나 잘못 구현되면 다수의 취약점이 생긴다.

## 7. 핵심 결론(Key Takeaways)

- MCP는 대규모 기업 환경에 그대로 배포하기에는 아직 프로덕션 준비가 되지 않았다("far from it"). 대규모 롤아웃 시 많은 문제·취약점을 예상해야 한다.
- AI 보안은 결국 여전히 IT 보안이다. 이번 발표에서 보여준 것들은 환각(hallucination)이나 프롬프트 인젝션 같은 LLM 고유의 새로운 취약점이 아니라, 인증·인가·신원 및 접근 관리(IAM), 공급망 리스크 같은 전통적 IT 보안 문제다.
- 샌드박싱·격리가 중요하다. 개인 장비에서 MCP 서버가 백도어에 감염돼 지속적 RCE를 얻는 것과, 격리된 샌드박스 환경에서 동일한 일이 벌어지는 것은 피해 규모가 크게 다르다.
- 공급망은 계속 변한다(코드가 바뀌고 메인테이너가 바뀐다). 프로덕션 AI 워크로드를 운영한다면, 백도어 삽입·오염·드리프트(drift)가 없는지 주기적으로 검증해야 한다.

## 8. Q&A — 학습 자료 추천 및 추가 논의

- **MCP·AI 펜테스트 학습 시작점**: 청중 질문에 대해 발표자들은 APIsec University가 제공하는 무료 MCP 보안 코스를 추천한다. 코스 진행자(Corey)가 실제로 자신만의 MCP 서버를 직접 구축하는 과정을 라이브로 보여주며, 그 과정에서 새로운 공격 경로를 발견하기도 했다고 언급한다. "직접 만들고 부숴봐야 이론만 읽는 것보다 훨씬 많이 배운다"는 조언을 덧붙인다. 이 코스는 2025년 12월경 공개된 것으로 언급된다.
- Paul은 데모에서 사용한 스크립트를 채팅에 공유했다고 언급한다(현재 macOS용으로 개발돼 계산기 앱을 실행하는 예시지만, 원하는 명령으로 바꿔 실습해볼 수 있다고 설명).
- APIsec University는 별도로 MCP 보안 워크숍(조직 대상 비공개 진행, 주로 3~4월경 공개 세션 예정)도 운영한다고 언급한다.
- 청중 질문 "KPMG에 이미 MCP 보안 모범사례가 있는가?"에는, 두 발표자는 이 발표를 KPMG를 대표해서가 아니라 개인 자격으로 하고 있다고 전제하며, KPMG 내부에는 더 큰 틀의 "신뢰할 수 있는 AI 프레임워크(Trusted AI Framework)"가 있어 MCP에도 일부 적용되지만 MCP 전용의 공개된 프레임워크는 아직 없다고 답한다. 다만 OWASP GenAI 프로젝트 쪽에서 최근 MCP 관련 리소스가 나왔다고 언급한다.
- 마지막 질문 "에이전틱 챗봇에서 프롬프트 인젝션이 여전히 가능한가?"에는 "매우 그렇다(yes, very much)"고 답하며, 가드레일 점검과 오늘 다룬 것과 같은 별도 공급망 공격 벡터 점검을 모두 함께 봐야 한다고 마무리한다.

- KPMG의 "Trusted AI Framework" 관련 언급은 발표자가 개인 자격으로 언급한 내용이며, KPMG의 공식 발표 자료로 별도 확인이 필요하다.
