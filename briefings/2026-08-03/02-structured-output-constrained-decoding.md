# 오늘의 AI 개념: 구조화된 출력과 제약 디코딩(Structured Output & Constrained Decoding)

> 작성일: 2026-08-03 · 분류: ai-concept

## 한 줄 정의

구조화된 출력은 LLM이 자유 텍스트가 아니라 미리 정의한 JSON 스키마에 100% 부합하는 형식으로만 답하도록, 생성 단계에서 문법적으로 강제하는 기술이다.

## 쉬운 설명

원래 LLM에게 "JSON으로만 답해줘"라고 프롬프트로 부탁하면, 모델은 대개 맞는 형식으로 답하지만 가끔 따옴표를 빼먹거나 필드를 누락하거나 설명 문장을 앞뒤에 붙인다. 그러면 개발자는 `JSON.parse()` 에러를 잡고 재시도 로직을 짜야 한다. 이건 마치 손글씨로 정해진 양식을 채우라고 "부탁"하는 것과 같다 — 대부분은 지키지만, 완벽하지는 않다.

제약 디코딩은 접근 자체를 바꾼다. 모델이 다음 토큰을 고를 때, 스키마를 어기는 토큰은 애초에 후보에서 제외해버린다. 즉 "부탁"이 아니라 "그 칸에는 숫자만 쓸 수 있는 인쇄 양식"을 주는 셈이다. 결과적으로 파싱 실패율이 사실상 0%가 된다.

기존의 "프롬프트로 JSON 요청하기"는 성공률 80~95% 수준이고, "함수 호출(Tool Use)"은 스키마를 힌트로만 참고해 95~99% 수준이다. 반면 JSON 스키마 기반 제약 디코딩은 토큰 생성 단계에서 타입·값을 강제해 100%에 가까운 준수율을 낸다는 점이 근본적으로 다르다.

## 동작 원리

1. 개발자가 JSON 스키마(또는 Pydantic 모델 등)로 원하는 출력 구조를 정의한다.
2. 이 스키마는 문법(grammar)으로 컴파일된다 — "이 위치에서는 문자열만, 저 위치에서는 열거값 중 하나만" 같은 규칙 트리로 변환.
3. 모델이 토큰을 한 개씩 생성할 때마다, 문법에 어긋나는 토큰은 확률 분포에서 마스킹(제외)된다.
4. 그 결과 모델은 문법적으로 허용된 토큰 중에서만 골라 다음 글자를 채운다.
5. 같은 스키마로 반복 호출하면 컴파일된 문법이 캐시되어(예: 24시간) 이후 요청은 빨라진다.

## 구체 예시·사례

Anthropic API에서는 Pydantic 모델을 정의하고 `client.messages.parse(model="claude-opus-5", output_format=ContactInfo)`처럼 호출하면, 응답이 파싱 없이 곧바로 `response.parsed_output`으로 타입 안전하게 나온다. 이메일 본문에서 이름·이메일·관심 플랜·데모 요청 여부를 추출하는 작업이라면, 모델이 필드를 빼먹거나 타입을 틀리는 경우가 원천적으로 발생하지 않는다. 오픈소스 진영에서는 vLLM·SGLang·TensorRT-LLM이 2026년 3월부터 XGrammar를 기본 제약 디코딩 백엔드로 채택해, 토큰당 40마이크로초 미만의 오버헤드로 JSON 생성을 강제하고 있다.

## 비슷한 것과 비교

| 방식 | 준수율 | 방법 | 한계 |
| --- | --- | --- | --- |
| 프롬프트로 JSON 요청 | 80~95% | 자연어로 형식 지시 | 가끔 스키마 이탈, 재시도 필요 |
| 함수 호출(Tool Use) | 95~99% | 스키마를 힌트로 제공 | 완전 강제는 아님 |
| 제약 디코딩(구조화 출력) | ~100% | 생성 단계에서 토큰 마스킹 | 재귀 스키마·수치 범위 제약 등 일부 미지원 |

선택 기준: 사람이 읽는 요약문처럼 형식이 느슨해도 되면 프롬프트로 충분하지만, 다운스트림 시스템이 파싱 실패를 절대 허용할 수 없는 데이터 추출·자동화 파이프라인이라면 구조화 출력을 써야 한다.

## 왜 지금 중요한가

XGrammar는 2026년 3월부터 vLLM·SGLang·TensorRT-LLM의 기본 구조화 생성 백엔드로 채택되며 업계 표준처럼 자리잡았고, Anthropic도 Claude 4.5 이상 모델과 API에 구조화 출력(JSON Outputs·Strict Tool Use)을 정식 지원한다. 이는 AWS Bedrock, Google Cloud Vertex AI, Microsoft Foundry 등 주요 클라우드에서도 함께 제공된다.

## 회계법인 AI 직무 연결 포인트

감사 증빙(세금계산서, 계약서, 리스 계약)에서 금액·날짜·계정과목 같은 필드를 자동 추출할 때, 파싱 실패나 필드 누락은 감사 증적의 신뢰성 자체를 흔든다. 구조화 출력을 쓰면 "추출된 금액이 항상 숫자 타입이고, 계정과목은 사전에 정의한 코드값 중 하나"임을 시스템 레벨에서 보장할 수 있어, 후속 검증·전표 매칭 로직이 훨씬 단순해진다.

또한 IFRS 18 도입처럼 대량의 과거 전표를 재분류해야 하는 프로젝트에서, AI가 추출한 결과를 엑셀·ERP에 바로 적재하려면 스키마 준수가 필수적이다. 구조화 출력은 "AI가 만든 데이터를 사람이 다시 손으로 다듬는" 작업을 줄여, 감사인이 판단이 필요한 예외 건에만 집중하게 해준다.

## 핵심 용어·논쟁

- **JSON 스키마(JSON Schema)** — 데이터의 구조·타입·필수 필드를 정의하는 표준 명세.
- **그래머 컴파일(Grammar Compilation)** — 스키마를 토큰 단위 허용/차단 규칙으로 변환하는 과정.
- **토큰 마스킹(Token Masking)** — 문법에 어긋나는 다음 토큰 후보의 확률을 0으로 만드는 기법.
- **Strict Tool Use** — 함수 호출 시 도구 이름·입력값까지 스키마 검증을 강제하는 옵션.
- 진행 중인 논쟁: 제약 디코딩이 형식은 완벽히 보장하지만, 모델이 스키마에 억지로 값을 끼워 맞추느라 답의 "내용" 품질(추론 정확도)이 오히려 떨어질 수 있다는 우려가 있다 — 형식 100%가 사실 정확도 100%를 의미하지 않는다는 지적이다.

## 자료 깊이 읽기

### Anthropic 공식 문서 — Structured Outputs — 영문/공식문서/중급
Claude 4.5 이상 모델에서 JSON Outputs(`output_config.format`)와 Strict Tool Use(`strict: true`) 두 기능을 직접 확인했다. Pydantic 모델을 `output_format`에 넘기면 `response.parsed_output`으로 타입 안전한 결과를 받는 코드 예시가 제공되며, 재귀 스키마·수치 범위 제약(`minimum`/`maximum`) 등은 아직 지원하지 않는다는 제약사항도 명시돼 있다. 첫 호출은 문법 컴파일로 지연이 있지만 이후 24시간 캐시된다.

### Structured Output Engineering 2026 — 영문/블로그/입문~중급
프롬프트 기반(80~95%) → 함수 호출(95~99%) → 제약 디코딩(~100%)으로 이어지는 3단계 접근을 정리했다. vLLM·SGLang·TensorRT-LLM이 XGrammar를 기본 백엔드로 채택해 토큰당 40마이크로초 미만 오버헤드로 JSON을 강제한다는 수치를 확인했다.
