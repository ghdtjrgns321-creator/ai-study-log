# 오늘의 AI 개념: 인텔리전트 터미널(Intelligent Terminal) 0.2

> 작성일: 2026-08-18 · 분류: agentic-coding

## 한 줄 정의

마이크로소프트가 만든 AI 네이티브 터미널로, 탭·창(pane)마다 서로 다른 코딩 에이전트를 동시에 배정하고 로컬 모델까지 직접 연결할 수 있는 멀티 에이전트 작업대다.

## 쉬운 설명

일반 터미널은 한 번에 하나의 셸 세션만 다룬다. 인텔리전트 터미널은 여기에 "에이전트 배차" 개념을 얹어, 탭 1은 GitHub Copilot, 탭 2는 Claude, 탭 3은 오픈소스 OpenCode처럼 서로 다른 에이전트를 각자 독립된 대화 이력으로 병렬 실행하게 한다. 비유하자면 콜센터 매니저가 여러 상담원을 각자 다른 창구에 배치해 동시에 다른 업무를 처리시키는 것과 비슷하다.

기존 Claude Code나 Copilot CLI가 "터미널 위에서 에이전트 하나를 잘 쓰는" 방식이었다면, 인텔리전트 터미널은 "여러 에이전트·여러 모델을 터미널 자체가 배차하는" 레이어에 가깝다. 즉 에이전트 하네스가 아니라 에이전트를 담는 그릇(컨테이너 애플리케이션) 역할을 한다.

## 동작 원리

1. `/agent` 슬래시 명령으로 탭마다 사용할 에이전트를 지정 — 각 탭은 독립된 대화 이력을 유지한다.
2. WSL 프로필 단위로도 에이전트를 배정할 수 있어, Windows용 에이전트와 리눅스(WSL) 내부에서 실행되는 에이전트를 분리 운용한다.
3. OpenCode가 1급 내장 에이전트로 편입되어 Agent Pane 안에서 채팅과 Autofix(자동 버그 수정) 워크플로를 바로 쓸 수 있다.
4. 로컬 모델 지원(BYOM, Bring Your Own Model)이 추가되어 OpenAI API 호환 엔드포인트(예: Ollama)를 연결하면 클라우드 의존 없이 오프라인으로 에이전트를 돌릴 수 있다.
5. Agent Pane 자체도 마우스 내비게이션, 프롬프트 히스토리, 토큰 사용량 표시 등으로 개선되었다.

## 구체 예시·사례

개발자가 배포 스크립트 작성은 Copilot 탭에, 레거시 코드 리뷰는 Claude 탭에 맡기고, WSL Ubuntu 프로필에는 로컬 Ollama 모델을 BYOM으로 연결해 사내 민감 코드를 클라우드로 보내지 않고 정적 분석을 돌리는 식의 조합이 가능해진다. 세 작업은 각자의 탭에서 독립된 대화 맥락을 유지한 채 동시에 진행된다.

## 비슷한 것과 비교

| 도구 | 초점 | 강점 | 한계 |
|---|---|---|---|
| Claude Code / Copilot CLI | 단일 에이전트 심화 | 깊은 컨텍스트, 서브에이전트 체계 | 터미널 안에서 다른 벤더 에이전트와 병렬 전환이 번거로움 |
| Zed 병렬 에이전트(08-09 다룸) | 에디터 내 다중 에이전트 | 에디터 통합, ACP 표준 | 터미널 네이티브 워크플로와는 결이 다름 |
| 인텔리전트 터미널 0.2 | 터미널 자체의 에이전트 배차 | 탭·WSL 프로필 단위 에이전트 분리, 로컬 모델 지원 | 아직 마이너 버전(0.2), 서드파티 에이전트 생태계 초기 단계 |

터미널 안에서 여러 벤더 에이전트를 바꿔가며 병렬로 굴리고 싶다면 인텔리전트 터미널이, 하나의 벤더 에이전트를 깊게 파고들고 싶다면 기존 CLI 하네스가 적합하다.

## 왜 지금 중요한가

Intelligent Terminal 0.2는 2026-08-10 마이크로소프트 공식 devblog를 통해 발표됐다. GitHub Copilot의 Agent Plugins 1.0 GA(2026-08-10, 이전 브리핑에서 다룬 오픈 표준의 실제 구현)와 거의 같은 시점에 나온 것으로, 에이전틱 코딩 툴링이 "하나의 에이전트를 잘 쓰는" 단계에서 "여러 에이전트를 동시에 배차·관리하는" 단계로 넘어가고 있음을 보여준다.

## 회계법인 AI 직무 연결 포인트

회계법인의 IT감사·데이터분석팀이 감사 스크립트(전표 추출, 이상거래 탐지 코드 등)를 작성할 때, 민감한 재무 데이터를 다루는 로컬 모델(BYOM) 탭과 외부 문서 검색용 클라우드 에이전트 탭을 물리적으로 분리 운용할 수 있다는 점이 눈에 띈다. 즉 "이 작업은 반드시 로컬 모델로만, 저 작업은 클라우드 에이전트로"라는 데이터 반출 통제를 터미널 단위에서 강제할 수 있어, 감사증거·클라이언트 데이터의 외부 유출 리스크를 낮추는 실무 통제 수단으로 응용 가능하다.

또한 여러 에이전트를 병렬로 배차하는 구조는 감사 워크페이퍼 자동화 스크립트를 벤더별로 나눠 검증(예: Copilot이 짠 코드를 Claude 탭에서 교차 리뷰)하는 이중 검토 워크플로에도 활용할 수 있다.

## 핵심 용어·논쟁

- **BYOM(Bring Your Own Model)** — 벤더가 제공하는 클라우드 모델 대신 사용자가 지정한(로컬 포함) 모델 엔드포인트를 연결하는 방식.
- **Agent Pane** — 터미널 안에서 에이전트 대화·도구 호출 상태를 보여주는 전용 패널.
- **Autofix** — OpenCode가 제공하는, 오류를 감지해 자동으로 수정 제안·적용까지 수행하는 워크플로.
- **WSL 프로필 단위 배정** — Windows Subsystem for Linux의 개별 배포판마다 별도 에이전트를 지정하는 기능.

2. 회계법인에서 로컬 모델(BYOM) 탭과 클라우드 에이전트 탭을 분리 운용한다면, 어떤 업무를 각각에 배정하는 것이 데이터 통제 관점에서 합리적인가?
3. 탭마다 독립된 대화 이력을 유지하는 구조가 감사 워크페이퍼 작업의 재현성(reproducibility)에 어떤 리스크를 만들 수 있는가?
